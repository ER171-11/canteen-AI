# ADR-012 跨端数据同步（桌面端 ↔ 云端）【草案 · 未来项】

- 状态：**草案（未来项）· 依赖 ADR-010 Phase 1–3（云端 PostgreSQL 主存 + 每店一行 JSONB）**
- 日期：2026-10-28（骨架）
- 关联：ADR-011（数据 schema 版本化 + 桌面端自动更新，**本 ADR 填补其文末「跨端数据同步」口子**）、ADR-010（云端单一主存，D0–D3 已拍板）、ADR-009 §2.1（服务端为真 / 客户端只读热备）、ADR-006（幂等 / rev）
- 前置：ADR-010 Phase 1–3 完成（云库可读写、rev 正确、`casWrite` 冲突返回 409、契约测试对真库转 VERIFIED）

---

## 0. 定位与边界

ADR-011 仅解决「升级不丢数据（`migrateOnBoot`） + 检查更新（`electron-updater`）」，**刻意不覆盖**终端本地 `snapshot.json` ↔ 云端的双向数据流动。本 ADR 填补该口子。

**铁前提（来自 ADR-010 D3）**：云端 PG 是唯一主存，**严禁双写**；桌面端是「云主存的只读缓存 + 写动作入队客户端」，**不存在任何本地账本写**。因此本 ADR 不需要设计「离线冲突合并 / rev 分叉」——那被 ADR-010 §9 明确否决（离线只读）。

### 范围
- **In**：① 首启全量拉取；② 运行期增量同步；③ 断网只读降级（沿用 ADR-009/010，仅确认桌面端对齐）；④ store 身份与鉴权；⑤ schema 版本闸门。
- **Out（归 ADR-010）**：云库建表、CAS 乐观锁、worker 执行、迁移切流。本 ADR 只消费这些能力。

---

## 1. 背景 / 问题

ADR-010 Phase 2 把每店 `snapshot.json` 一次性灌入云端 `snapshots(store_id, rev, data JSONB)` 并切主后，桌面端仍持有本地 `snapshot.json`。若不做跨端同步：

1. 桌面端读到的永远是切流那天的旧快照，云端后续所有业务写不可见；
2. 桌面端「升级不丢数据」只对本地缓存生效，与云端真值脱节；
3. 多店场景下，任一店的桌面端看不到其他店的实时状态（集中价值落空）。

目标：**桌面端首启拉全量、之后增量跟随、断网回退只读**，形成「云主存 → 桌面只读缓存」的完整闭环。

---

## 2. 设计骨架

### 2.1 store 身份与鉴权（当前缺口）
ADR-010 按 `store_id` 分店，但桌面端目前**无云身份**。必须补：
- 设备/门店绑定：登录云 BFF → 下发 `store_id` + 短时令牌（走 CAM / 云鉴权，属 ADR-010 §7.1 未验证项）；
- 本地仅缓存令牌，不缓存账本语义写；
- 多店切换 = 换 `store_id` 拉对应行。

### 2.2 首启全量拉取
- 触发：桌面启动、`electron-updater` 检查完、BFF 起好后；
- 动作：BFF 持 `store_id` 向云 BFF 取该行 `data`（整行 JSONB）；
- 落盘：**原子写**——先写 `snapshot.json.tmp` 再 rename，避免半截文件；落盘后照常跑 `migrateOnBoot()`（本地缓存也要结构补齐，保证可读）；
- 失败：拉取失败**绝不清空**本地旧缓存，保留上次好状态并重试。

### 2.3 增量同步（rev 心跳 + 整行重拉）
ADR-010 §10 明确：每次动作＝**整行 JSONB 重写**，故「增量」不是行内 diff，而是**rev 变更驱动的重拉**：
- 轻量心跳：只返回 `rev`（小包，可高频轮询，如 10–30s）；
- rev 不变 → 无事；rev 变大 → 拉整行 `data` 并重命名落盘 + `migrateOnBoot()`；
- 轮询间隔、是否走 WebSocket 推送留作待定（见 §5）。

### 2.4 断网只读（沿用，仅对齐）
- 网络不可达 → 读本地 `snapshot.json` 上次好状态，UI 标「离线（只读）」；
- 写动作**停本地队列不丢**（ADR-004 §7.1，24h 过期），恢复后云端消费器自动续跑；
- **不做**本地离线写（与 ADR-010 §9 一致，本 ADR 不新立断网原则）。

### 2.5 schema 版本闸门（防旧客户端读不懂新云数据）
- 云行 `data.v`（schema 版本）> 本机 `SCHEMA_VERSION` → **拒绝应用**，弹「请更新客户端」并触发 `electron-updater`（`CANTEEN_UPDATE_URL` 可覆盖源）；
- 这样「升级不丢数据」与「跨端同步」在版本维度锁死：旧 app 不碰超纲数据，新 app 拉到即迁移。

---

## 3. 触发时机总览

| 时机 | 动作 |
|---|---|
| 启动（BFF 起后） | 首启全量拉取（或本地已有则跳过重拉，仅做 rev 对齐） |
| 周期轮询 | rev 心跳；变化则整行重拉 |
| 显式「立即同步」 | 新增「数据同步」入口（**区别于** `app:check-update` 的「应用版本检查」） |
| 断网恢复 | 立即一次全量 rev 对齐 |
| 拉到超纲 schema | 拒绝 + 提示升级客户端 |

---

## 4. 一致性 / 容错红线（继承 ADR-006/010）
- 本地 `snapshot.json` 仅缓存，**不构成账本**，任何写只走云端队列（红线①唯一写入口不破）；
- 拉取落盘原子化（tmp + rename），失败保留旧缓存；
- 不双写、不本地 merge、不 rev 分叉；
- 本地缓存 `rev` 永远 ≤ 云端 `rev`；health 暴露 `cloud_rev / local_rev / last_sync_at` 便于核验收敛。

---

## 5. 待澄清 / 待决策（草案阶段不拍板）
1. 增量推送：轮询 vs WebSocket 服务端主动推（需云 BFF 长连接能力，评估成本）；
2. 大快照重拉成本：单店多年销售暴涨后整行重拉是否引入「行级业务表」拆分（ADR-010 §10 已知上限，二次重构触发条件）；
3. 多店同端切换的本地缓存隔离（按 `store_id` 分目录 or 单文件换键）；
4. 云鉴权形态：CAM 子账号 / 临时令牌有效期 / 刷新策略；
5. 首启拉取与 `migrateOnBoot` 的顺序与失败回滚边界（先落盘再迁移，还是先迁移云数据再落盘）。

---

## 6. 验收标准（未来，ADR-010 Phase 1–3 完成后）
1. 桌面端首启能从云拉到本店整行 `data` 并可读，本地 `rev` 与云端一致；
2. 云端一次业务写后，桌面端在轮询窗口内 rev 收敛、数据可见；
3. 断网期间桌面只读、队列不丢，恢复后自动续跑并收敛；
4. 云 schema 升级后，旧客户端拒绝超纲数据并正确提示升级；
5. 拉取失败不破坏本地缓存，tmp+rename 原子落盘可验证。

---

## 7. 不做什么 / 风险
- ❌ 不做离线写 / 冲突合并（ADR-010 §9 已否决）；
- ❌ 不设计云库本身（归 ADR-010）；
- ❌ 在 ADR-010 Phase 1–3 完成前写任何同步实现代码（避免重复劳动、避免在主存形态未定上叠层）；
- 风险：store 身份/鉴权是全新缺口，需与云端部署一并设计，不能等切流前才补。
