# 演练环境使用说明（沙箱库隔离）

> 目的：测试系统功能时不再污染真实数据。
> 真实主库 `store-inventory/data/餐厅系统.db` 只读保护，测试一律写入**演练库**。

## 1. 两套环境对照

| | 真实环境 | 演练环境 |
|---|---|---|
| 入口 | `启动测试.cmd` | `启动演练.cmd` |
| 库文件 | `store-inventory/data/餐厅系统.db` | `store-inventory/data/餐厅系统_演练.db` |
| 备份目录 | `data/backups/` | `data/backups_sandbox/` |
| 环境变量 | `CANTEEN_ENV=real`（缺省） | `CANTEEN_ENV=sandbox` |
| 前端标识 | 无 | 顶部黄色横幅「演练环境 · 数据非真实」 |
| 落库端 | 需自行启动 consumer | 启动脚本自动拉起 consumer + pusher |

**结论：只要做功能测试，一律用 `启动演练.cmd`。**

## 2. 演练库管理

```bash
node scripts/sandbox-db.js --status        # 看两库路径/大小/rev/单据计数
node scripts/sandbox-db.js --init          # 从主库生成演练库（已存在则拒绝）
node scripts/sandbox-db.js --reset         # 丢弃并重建（测试跑脏了就用它）
node scripts/sandbox-db.js --drop          # 仅删除演练库
node scripts/sandbox-db.js --print-path    # 只输出演练库绝对路径（脚本用）
```

- 复制方式：优先 SQLite `VACUUM INTO`（页级一致），失败回退整文件复制。
- 生成时会清空演练库的 `snapshots` 历史，避免体积膨胀与误导回滚。

## 3. 环境守卫（防误写真实库）

`bff/lib/env-guard.js` 在启动时做强制校验：

| 配置 | 行为 |
|---|---|
| `CANTEEN_ENV=sandbox` 且库=主库 | **拒绝启动**（exit 1），并打印修正命令 |
| `CANTEEN_ENV=real` 且库=演练库 | 告警，并按 sandbox 处理 |
| `CANTEEN_ENV=sandbox` 且库=自定义路径 | 告警，放行 |
| 其它 | 静默 |

覆盖的进程：`bff/store-node/server.js`（店内节点）、`bff/store-node/consumer.js`（落库端）。

环境同时透出给前端：`GET /api/health` → `{ env: 'real' | 'sandbox' }`，前端据此显示演练横幅。

## 4. 真实单据导入（采购单/入库单）

真实配送单在 `store-inventory/订单/`（8 个 xlsx + 3 个 xls）。

**务必先干跑复核，再正式导入：**

```bash
# ① 干跑（不写库；建议先指向演练库，零风险）
node bff/store-node/seed/import_orders_excel.js \
  --dir store-inventory/订单 \
  --db store-inventory/data/餐厅系统_演练.db --dry-run

# ② 复核通过后，正式导入真实主库
node bff/store-node/seed/import_orders_excel.js \
  --dir store-inventory/订单 \
  --db store-inventory/data/餐厅系统.db

# ③ 推快照给 BFF，前端立即可见
node bff/store-node/pusher.js --once --db store-inventory/data/餐厅系统.db --token <BFF_TOKEN>
```

命令行参数（`import_orders_excel.js`）：`--dir` 订单目录 · `--db` 目标库 · `--dry-run` 只预览 · `--push` 导入后推 BFF。

### 干跑结果参考（2026-10-09 实测）

```
[before] ings=96  stock>0=93  recv=9   logs=183
[after ] ings=164 stock>0=162 recv=13  logs=227
[stat  ] new_recv=9  new_ing=68  skipped=1
```

两点必须人工确认后再落库：

1. **会新增 68 个原料**（`ings 96→164`）——导入器按单上品名自动建料，可能包含别名/重复项，需要与现有主数据核对。
2. **单据覆盖多家门店**——文件名显示涉及「熊猫五福 / 熙曦五福 / 鸿源五福 / 鹏翔五福」，若只要本店数据，需先筛掉其它门店的表格。
3. 导入会**同步更新库存与均价**（`stock`、`avg`），这是把库存维护成真实值的入口。

## 5. 常见问题

| 现象 | 处理 |
|---|---|
| `启动演练.cmd` 报「端口已被占用」 | 说明有真实环境进程在跑，先运行 `停止演练.cmd` 或关掉对应窗口；这是**故意的保护**（避免复用连主库的进程） |
| 演练数据写脏了 | `node scripts/sandbox-db.js --reset` 后重启演练环境 |
| 前端没出现演练横幅 | 检查 BFF 是否由演练启动脚本拉起（需 `CANTEEN_ENV=sandbox`），`curl http://127.0.0.1:8787/api/health` 看 `env` 字段 |
| consumer 报「拒绝启动」 | 配置为 sandbox 但库指向主库，按提示设置 `STORE_DB` 或改 `CANTEEN_ENV=real` |
| 想确认测试有没有写进主库 | `node scripts/sandbox-db.js --status` 对比两库 `rev` 与单据计数 |

## 6. Linux / macOS

```bash
CANTEEN_ENV=sandbox ./scripts/dev-up-native.sh   # 自动切演练库并生成（若缺失）
CANTEEN_ENV=sandbox ./scripts/dev-up-lan.sh      # 局域网联调同理
```

脚本会识别 `CANTEEN_ENV`：sandbox 时自动把 `STORE_DB` 指向演练库（不存在则先 `--init`），并 `export` 给子进程。

## 7. 收口清单（每次动过数据后自查）

```bash
node scripts/sandbox-db.js --status          # 主库 rev 是否被测试改动
node scripts/scan-mock-usage.js --check      # 界面是否还有假数据残留
git status --short                           # 是否有运行态文件混入
```
