### W2 · 商品库（原料）结构化字段 + 受控词表 Tag 模式

> **依据《商品数据库架构优化方案》（`docs/商品数据库架构优化方案.docx`）升级**：原「纯 Tag 模式」存在同义词泛滥（「红色/红/大红/赤色」并存）、数据标准化风险高、后续清洗成本高、与供应链对成本核算/合规追溯的刚性需求不匹配等隐患，故从「纯 Tag」升级为**「结构化字段 + 受控词表驱动的多值标签」双轨制**。

**现状**：`ings` 字段 `id,name,cat,unit,buy,conv,spec,stock,avg,...,safe,yld,on` 无产地/厂商/颜色/部位字段，只能挤在 `name`（「东北酸菜(切丝)」「食用墨鱼汁」）或 `spec`；录入靠自由文本，同一属性多种表述；搜索散落各页本地过滤，无统一检索。

**方案（双轨制，落「甲+丙」补字段优先）**：

1. **结构化字段（数据底座）**：核心属性（品类、单位、产地、品种、等级、规格、包装方式等）设为**固定下拉选项**，选择式录入替代纯文本，从源头保证机器可读；`cat` 收敛枚举（与 W4 联动）。
2. **固定词条 Tag（受控词表，灵活层）**：产地/颜色/部位/等级等建模为**受控词表** `term{id, name, category, aliases[]}`；录入人**多选关联标准词条**（而非自由输入），词条由专人维护、走「词条申请→审核→上架」迭代；别名（「新疆/新疆产地/产自新疆」）归一到同一词条 ID。
3. **SKU 字段 ↔ Tag 映射**：`ings` 标准字段值**自动映射为基础 Tag（不可手改）**；运营可另加**营销类自定义 Tag**（如「夏季清仓」「直播间主推」），与业务属性 Tag 分离，兼顾严谨与灵活。
4. **搜索精确化**：检索基于**词条 ID 精确匹配**（词条规范化层把用户输入映射到标准词条 ID），不靠 `name/spec` 模糊碰运气。

**改动点**：`ALTER TABLE ings ADD COLUMN tags TEXT`（存词条 ID 数组 + 少量自定义 Tag）；新增受控词表 `ing_terms`（或轻表）+ 词条审核写侧 `term.upsert` 进 `registry.js`；写侧加 `ing.attr_set`；`routes/inventory.js` 返回 tags 并支持词条 ID 命中；前端 StockPage 改为下拉/多选词条录入 + 命中高亮。

**验收**：搜「东北」命中产地词条、搜「里脊」命中部位词条、搜「墨鱼」命中颜色词条（词条 ID 精确匹配，无遗漏）；「新疆/新疆产地/产自新疆」归一同一词条；tag 不影响 `recipe_cost.js` 成本与 `ing_alias` 匹配。

**落地记录（2026-10-19 已交付）**：
- 数据模型：`ings[].tags`（JSON 对象字段，无需 DDL，同 W4 `type` 手法），存受控词条 ID 数组 + 自定义营销 Tag；`data.ing_terms` 存受控词表 `term{id,name,category,aliases[],status}`。
- 新增 `bff/lib/ing_terms.js`（8 个受控维度白名单 / 别名归一 / 词条 ID 精确命中 / `seedTerms` 开箱种子）；`bff/lib/algorithms/terms.js`（`term.upsert` 词条申请→审核→上架、`ing.attr_set` 关联词条+自定义 Tag，未上架词条拒选）。
- 注册与路由：`registry.js` 注册 `term.upsert` / `ing.attr_set`；`routes/inventory.js` 加 `GET /api/inventory/ing-terms`（词表）与 `/ing-terms/match?q=`（词条 ID 命中，只读）。
- 前端：`types.ts` 补 `IngTerm` / `IngItem.tags` / `SnapshotData.ing_terms`；`api/index.ts` 补 `fetchIngTerms` / `fetchIngTermsMatch` / `submitTermUpsert` / `submitIngAttrSet`；`StockPage.tsx` 编辑 Modal 多选词条录入（按维度分组、待审禁用）+「词条管理」入口 + 新增「标签/属性」列 + 搜索词条 ID 命中高亮。
- 测试：`terms.test.js` 单测（别名归一 / 命中 / 申请审核 / 非法引用 / 未上架拒选）+ 算法层 22/22 全绿；前端 `tsc --noEmit` 通过。

### W4 · 原料库消耗品治理（食材 / 耗材分离）

**现状**：`ings` 同时承担食材与低值易耗品（手套/口罩/保鲜袋/硅胶布/蒸冠），`cat` 自由文本半失控（`其他`19 项错位、干调混入主食菌菇、同名重复）；真实配送单将新建 68 项原料中 **5 项是耗材**。详见 `docs/待治理-原料主数据与低值易耗品同库问题.md`。

**方案（落「甲+丙」）**：`ings.type = 'food' | 'consumable'` 语义分层（存量默认 food）；`cat` 收敛枚举（含「耗材包材」）；报表按 `type` 过滤。与《商品数据库架构优化方案》「消耗品（MRO 物料）必须打『辅助耗材』标签、不得进入核心原料 BOM 计算逻辑」口径一致——本方案 `type='consumable'` 即对应「辅助耗材」标签。

**改动点**：`ings[].type` 为 JSON 对象字段（无需 DDL，`ings` 非 SQLite 表）；`import_orders_excel.js` 的 `findIng`/`createIng`（`:632-672`）加 type 识别；成本/损耗/比价/补货/经营分析五处按 `type='food'` 过滤；回灌 `待治理-新增原料清单.csv`（68 行）写回 `cat/buy/conv/safe/type`（`type` 已回灌，剩 `cat/buy/conv/safe`）。

**决策纪要（2026-10-19 已拍板，10/10 有结论）**：

1. **边界**：手套/口罩/保鲜袋/清洁用品/包材/餐具损耗/蒸笼布·硅胶布/劳保；判定标准=「不进菜品成分 + 一次性使用」。
2. **是否进成本**：不进，单列「营业费用-低值易耗」。
3. **损耗率分母**：仅食材采购额，耗材损耗单独统计。
4. **是否参与比价**：初期不做。
5. **是否参与补货**：不参与预测，改「安全库存阈值提醒 + 人工下单」。
6. **谁维护**：库管，在「原料库存」页新增耗材标签页；导入自动识别 + 人工确认。
7. **存量处理**：加 `type` 默认 `food`，人工归位 19 项错位分类 + 标记 5 项耗材。
8. **计量口径**：`conv`/`buy` 同食材规则（保鲜袋「1件=20卷」照实填），`yld=1`。
9. **报表口径**：默认只统计食材，耗材单独展示。
10. **迁移节奏**：一步到位（加 `type` + `cat` 收敛枚举 + 回灌 CSV 同时写 `type`/`cat`）。

**验收**：耗材 `type='consumable'`，不进菜品成本/损耗率分母/补货/比价；库存总值可拆食材/耗材展示。

### W5 · 检索域隔离 + 搜索索引字段管控（竖切数据库）

> 依据《商品数据库架构优化方案》补充：除「业务域隔离」外，新增**「搜索索引字段白名单」**（税号 / 供应商内部编码 / 成本价等敏感字段严禁进入搜索索引）。该方案另提「按品类逐层拆表（冻品 / 禽蛋 / 蔬菜 / 干调）」，属长周期架构项，与本版红线「补字段优先、慎建新表」冲突，故本版**只落检索域隔离 + 索引字段管控**，品类拆表列为后续专项评估。

**现状**：无统一检索层、各页本地搜索；数据都在单一快照，无"业务域"维度；全库模糊搜索。痛点：搜"商品购买"带出税号等财务数据（"拔萝卜带出泥"）。

**方案**：定义业务域枚举 `商品采购/财务税务/食安/员工/设备/销售`；新增只读检索端点 `/api/search?domain=xxx&q=...` 按域切分；**索引字段白名单**（仅索引名称 / 规格 / 标准属性等必要字段，敏感字段不入索引）；全局搜索分域 tab，不跨域混排。

**改动点**：新增 `routes/search.js`（或并入 `modules.js`）按 domain 分发 + 索引字段白名单；前端全局搜索改分域 tab；与 W2 检索契约合并设计（W2=域内词条 ID 精确匹配、W5=域间隔离 + 敏感字段管控）。

**验收**：搜"商品购买"仅返回商品/采购域，税号 / 发票 / 分账 / 供应商内部编码不出现；各 tab 互不串味。

**落地记录（2026-10-20）**：

- `lib/search.js`（纯函数、零写库）：`DOMAINS` 六域枚举 + `DOMAIN_SOURCES` 各域索引定义（`dataKey` 优先 / `extKey` 兜底，与 supply.js 同口径）+ `SENSITIVE_FIELDS` 敏感字段黑名单（税号/内部编码/成本价/均价/金额/薪资/身份证/银行账号/余额，含中英文键名）。
- 双层隔离：**白名单**（每域仅索引 name/cat/spec/sup/role 等必要字段）+ **黑名单**（`matchRow` 检索前跳过敏感字段），验收「搜商品购买不带出税号」由双保险保障。
- `routes/search.js`（只读 GET）：`/api/search?q=` 全局分域、`/api/search?domain=&q=` 单域、`/api/search/domains` 域枚举；已注册进 `server.js` ROUTES。
- 与 W2 检索契约合并：W2 = 域内词条 ID 精确匹配（ing_terms），W5 = 域间隔离 + 敏感字段管控。
- `lib/search.test.js` 单测覆盖：税号/内部编码/成本价/金额/薪资/身份证不入索引、名称/规格可检索、单域不串味、全局分域。

### W6 · 菜谱 BOM 引入中间材料（半成品）

**现状**：`recipes`（`001_new_tables.sql:16`）字段 `sku_id,name,color,filling,face_main,main,aux,seasoning,params`，BOM 扁平直引原料；`recipe_cost.js` 的 `buildCostCard` 只展开到原料，`SKIP_NAMES={清水,料水}` 直接跳过，无中间材料/子配方概念。

**影响与改动点**：

1. **数据模型**：新增中间材料库（或 `recipes` 加 `type='semi'`），中间材料有自己的 BOM。
2. **BOM 展开**：`buildCostCard` 由"配方→原料"改为"配方→（中间材料→）原料"递归展开，**需防环**。
3. **成本归集**：中间材料成本 = 其 BOM 递归求和，`batch_cost/unit_cost/portion_cost` 口径不变。
4. **库存扣减**：出品扣减**倾向 (a)** 递归到底层原料（中间材料仅作"配方缩写"，不单独建库存，避免双轨）；走既有 rev 三向合并。
5. **影响面**：`recipe_cost.js`、`recipe_method.js`、库存重放、`menu_baoben`、结构测算 CALC 联动验证；`SKIP_NAMES` 的料水/清水从"跳过"改为"可选中间材料"。

**验收**：配方引用「料水」等中间材料能递归展开到原料、成本正确、无环、库存扣减正确。

**落地记录（2026-10-20）**：

- `recipe_cost.js`：`buildCostCard(recipe, data, semiLib)` 增第三参数（中间材料库 = `ext.recipes` 全量，自动筛 `type='semi'` 行；缺省回退 `data.semi_recipes`）。
  - `collectSemiIndex` 建「中间材料名 → recipe」索引；`semiBaseGrams` 定一批基准克重（优先 `params['一批出成_g']`，退化 BOM 克重合计）。
  - 核心 `expand(rec, scale, stack)` 递归展开：命中中间材料 → 按「引用量 / 基准克重」缩放后递归；`stack`（name/sku_id 祖先链）防环，命中即跳过不报 missing。
  - `SKIP_NAMES={清水,料水}` 由「硬跳过」改「可选中间材料」：命中中间材料库则展开，否则仍跳过（旧数据兼容、不编造成本）。
  - `module.exports` 增 `isSemi / collectSemiIndex / semiBaseGrams`。
- 调用点：`workbench/si_team/si_sim/si_knowledge/agent/tools/agent/export/modules/kitchen` 九处 `buildCostCard` 统一传 `ext.recipes`，能力即插即用。
- `lib/recipe_cost.test.js` 单测：中间材料递归展开成本正确、100g 料水等比缩放、防环不无限递归、嵌套半成品逐层展开、无库时旧口径跳过、复合行兼容。
- **下一步（数据侧）**：料水中间材料种子（`recipes` 加 `type='semi'` 行，BOM=花椒10g/大料5g/小茴香5g/香叶3g，`一批出成_g=200`）需店内端补充 + 同步 seed 平价对拍，避免本轮动 seed_recipes.js 的 Python 参考实现。
- 库存扣减**倾向 (a)**（递归到底层原料、中间材料不单独建库存）维持不变，本轮未动库存重放（BOM 展开只影响成本卡，扣减口径不变）。
