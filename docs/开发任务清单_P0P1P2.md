## 一、排期原则

1. **依赖优先**：先做共享底座（快照推送器、BFF 骨架、表 DDL、鉴权），再做依赖它的模块只读层，最后做写回闭环。
2. **只读先行**：每个模块先交付「只读快照 + UI 展示」，让老板先「看懂店」；写回动作一律后置到 P2 闭环。
3. **写回闭环后置**：所有写操作统一走 `App 确认 → 云端队列 actions_queue → 店内消费器 → /api/sync（带 rev 乐观锁）`，闭环放在 P2，P0/P1 只做「建议」态不触达。
4. **红线不破**：`rebuildStock()` / `dishRecipeCost()` / `seedDB()` 受保护逻辑全程零改动；用量换算只读调 `calcQtyOf`，成本只读调 `dishRecipeCost`；结算单只读输出层不写 DB；自动生成 ≠ 自动下单；色源锁定（红=火龙果等不可替换）。触禁区任务一律标「只读复用」。
5. **期序清晰**：P0 看店 → P1 问店 → P2 拍板，期与期之间允许并行收尾，但 P2 写回闭环必须在 P0/P1 只读层稳定后启动。
6. **工作量与时间解耦**：工作量只给 S/M/L，不给天数；甘特用相对周序（W1…Wn）表示排布与重叠，不作为工期承诺。

**关键路径**：`S8 表 DDL → S2 快照推送器 → S1 BFF 骨架 → S5 鉴权 → 厨房核心（recipes/sop_steps/sop_workorders/qc_records）→ M1 analysis 只读 → M4 pos 只读 → M6 booking 只读 → M7 foodsafe（含 Kimi 留样 sample）→ M2 staff → S9 首页增强 → Kimi 验货 recv 先行`

- 简报闭环：S2 + S1 `/api/report/daily` + S9 首页 → 老板每日 08:00 收简报。
- 进销只读：M4 pos 桌台/实收 + M6 booking 预订排队 + M1 analysis 趋势/热力/矩阵/效率。
- 厨房核心：recipes/sop_steps/sop_workorders/qc_records 入库 + 工单按开餐时间倒排。
- Kimi 验货 `recv`/留样 `sample` 先行（建议态，写回待 P2）。

### 5.2 P1 里程碑：AI 对话 + 外卖 + 会员 + 排班（Kimi 扩展）

**关键路径**：`S6 /api/kimi/vision 全量 6 用例 → S7 Kimi 前端集成 → M5 takeout → M3 vip → M11 review → M10 supply → M8 equipment → M2 staff Kimi uniform → AI 对话 /api/agent/chat`

- AI 对话：`/api/agent/chat` 调本地确定性函数（结构测算/库存/补货）+ LLM 生成卡片。
- 外卖/会员/口碑/供应链/能耗只读看板上线。
- 6 处视觉用例统一交互（`recv`/`stock`/`qc`/`plate`/`sample`/`uniform`），CTA 走确认台建议态。

### 5.3 P2 里程碑：写回闭环 + 财务分账 + 口碑闭环 + 损耗

**关键路径**：`S3 队列消费器 → S4 确认台/actions_queue 状态机 → M9 finance 分账 → M12 loss 报损 → 口碑改进措施闭环 → 各模块写回收口（M2/M3/M4/M5/M6/M7/M8/M10/M11 写回）→ 端到端落库验证`

- 写回闭环端到端：App 确认 → 云端队列 → 店内消费器 → `/api/sync`（带 rev）→ 快照回写「已执行」。
- 财务分账冻结/解冻、开发票审批、报损单审批、盘亏盘盈入档。
- 口碑改进措施改配方走版本化，新人培训上岗记录可追溯。
