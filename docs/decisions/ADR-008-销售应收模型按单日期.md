# ADR-008：销售应收模型——以「单日期」为主轴的口径决策

- 日期：2026-10-12
- 状态：**已定案**（批准人：William，2026-10-12 签署）
- 关联：ADR-006（写操作幂等边界）、ADR-009（服务端快照形态与销售/采购录入职责边界）、ADR-004（进货单录入边界，状态机对齐基准）
- 影响面：`data.sales[]` 数据模型（补 `discount` / `receivable` / `payments`）、`bff/routes/report.js`（应收/实收/欠款聚合）、`bff/lib/algorithms/pos.js`（销售录入/收款执行器）
- 触发：欠账总表「执行前置依赖」——应收/实收按「单日期」还是「收款日期」统计，阻塞 `FP-DASH-02/03/04/08`、`FP-SALE-07/08/11`
- 备注：本 ADR 为**口径前置决策**，只定口径，不定 UI 与写路径细节（写路径归属见 ADR-009 §职责边界）。

---

## 1. 背景

- 当前快照 `sales[]` 只有 `amount / qty / date / hour / channel / method` 六个字段，
  **没有 `discount` / `receivable` / `payments`**（这些是旧版 `DB.sales` 才有的字段）。
  证据：`docs/迁移基线/FP-经营概览.md` FP-DASH-08 处置列、`docs/迁移基线/FP-销售收银.md` 汇总结论。
- 由此连锁阻塞了四个只读 KPI 与三个写类动作：
  - `FP-DASH-02` 应收合计（按单日期）、`FP-DASH-03` 实收合计（按收款日期）、`FP-DASH-04` 未收欠款（累计）、`FP-DASH-08` 折扣/抹零（本期）——均缺数据源；
  - `FP-SALE-08` 顶部 KPI（本月应收/累计实收/未收欠款）依赖「单日期 vs 收款日期」口径；
  - `FP-SALE-11` 分次收款（应收 − 实收 = 欠款）需要应收/实收两个数才能算。
- 旧版这两张 KPI 卡的口径本就有明确字样：`应收合计（按单日期）`、`实收合计（按收款日期）`
  （`FP-经营概览.md` FP-DASH-02/03 旧版证据列）。因此本决策不是「新造口径」，而是
  **把旧版已经写死在卡上的口径正式登记为模型约束**，避免各端各自理解、口径漂移。

## 2. 决策

### 2.1 销售单是应收账款的最小单元，模型以「单日期」为主轴

每张销售单持有 `date`（单日期，即开单/成交日）。所有「应收」类统计一律按 `date` 归属，
不按「收款动作发生日」归属。这样销售单列表（FP-SALE-07）、应收 KPI（FP-DASH-02）、
欠款 KPI（FP-DASH-04）共享同一个「单」的主键与时间轴，不会出现「同一张单在应收和实收两处日期不同」的分裂。

### 2.2 应收口径：按单日期（`date`）

- **应收合计（本期）** = Σ 区间内 `sales[].date ∈ [start, end]` 的单据应收 `receivable`。
- 落到 FP-DASH-02 的「按单日期」字样；区间定义沿用阶段 13 已定的
  `[截止日-(r-1), 截止日]`（`docs/迁移基线/FP-经营概览.md` 口径提示）。

### 2.3 实收口径：按收款日期（`payments[].date`）

- **实收合计（本期）** = Σ 区间内 `payments[].date ∈ [start, end]` 的收款实收。
- 「收款」是**动作**，其时间维度天然是动作发生日，与「单日期」是两件事；
  分次收款（FP-SALE-11）会在不同日期产生多条 `payments`，故实收必须按收款日期归属。
- 落到 FP-DASH-03 的「按收款日期」字样。

### 2.4 欠款口径：应收 − 实收（累计）

- 单级：`欠款 = receivable − Σ payments`；店级：**未收欠款（累计）** = Σ 全部单的欠款。
- 「累计」不设时间区间上界（旧版 `saleDebt()` 汇总口径），与「本期应收/实收」的区间口径刻意区分。

### 2.5 数据模型扩展：`sales[]` 补齐三个字段

在 `sales[]` 每行补（旧版字段名保持一致，避免口径漂移）：

```
receivable   number  本单应收（= 原 amount 口径，可因折扣/抹零而小于售价合计）
discount     number  本单折扣/抹零金额（默认 0）
payments     array   收款记录 [{ date, amount }]（默认 []）
```

- `receivable` 与 `payments` 派生 `欠款 = receivable − Σ payments.amount`，不另存「欠款」字段
  （欠款是**派生值**，存下来必漂移，与欠账总表「汇总数是派生数据」同一教训）。
- 旧字段 `amount` 语义收敛为「本单原始成交额（售价合计）」，`receivable` 为其扣减折扣/抹零后的应收，
  两者关系、折扣/抹零的具体扣除口径在 FP-SALE-05（A–E 金额口径重算）落地时细化，本 ADR 不越界。

## 3. 为什么不是别的方案

| 备选 | 否决理由 |
|---|---|
| 应收与实收**都**按「单日期」 | 分次收款会让「今日实收」漏掉「收昨天欠款」的进账，老板看板「实收合计」失真，旧版也明确是「按收款日期」 |
| 应收与实收**都**按「收款日期」 | 应收按收款日归属会把「今天开的单、明天才收的钱」记到明天，FP-SALE-08「本月应收」与销售单列表日期对不上，无法追溯单 |
| 欠款存为快照字段（应收−实收落库） | 派生值落库必然与源数据漂移（改了收款不改欠款）；欠款只能实时推导 |
| 不补 `receivable`，继续用 `amount` 当应收 | `amount` 不含折扣/抹零，一旦上折扣（FP-DASH-08）应收就会被高估，且与旧版字段语义断裂 |

## 4. 保了什么

- **旧版字段名不换**：`receivable` / `discount` / `payments` 沿用旧版 `DB.sales` 字段名，平价（差分）测试有对照物。
- **派生值不落库**：欠款、毛利率一律实时算（红线 ① 的精神——算得对靠单源数据，不靠预存）。
- **口径唯一出口**：应收/实收/欠款三个数只在 BFF 聚合（`report.js`），前端不复算，
  与 ADR-007「前端不再持有量本利公式」同一原则。

## 5. 落地清单与实施状态

本 ADR 只定口径，实施随 `FP-SALE-07/08/11`、`FP-DASH-02/03/04/08` 同批推进（状态另在其卡片登记）。
此处仅登记「口径已解除阻塞」：

| 项 | 内容 |
|---|---|
| 应收口径 | 按单日期 `date` |
| 实收口径 | 按收款日期 `payments[].date` |
| 欠款口径 | 应收 − 实收（累计，派生） |
| 数据模型 | `sales[]` 补 `receivable` / `discount` / `payments`（旧版字段名） |
| 阻塞解除 | `FP-DASH-02/03/04/08`、`FP-SALE-07/08/11` |

## 6. 如何验证

落地后（非本 ADR 单独交付物）：
- `FP-DASH-02/03/04`：经营概览页三张 KPI 与旧版同口径数值一致（差分）；
- `FP-SALE-08`：顶部 KPI「本月应收」= 按单日期区间聚合，「累计实收」= 按收款日期聚合；
- 构造一张「昨日开单、今日收款」的单，断言：今日应收不计入、今日实收计入。

## 7. 副作用与遗留

- `amount` 与 `receivable` 的差（折扣/抹零）在 FP-SALE-05 落地前可能为 0，
  需避免 `FP-DASH-08` 被读成「本期无折扣」——沿用 FP-DASH-08 处置列「不先上 ¥0 假卡」的既有结论。
- 旧版 `payments` 的精确结构（是否含渠道/方式/备注）尚未在源码侧逐字段核对，
  落地 `FP-SALE-11` 时需回填并补差分用例；本 ADR 只锁定「按收款日期归属」这一口径。
