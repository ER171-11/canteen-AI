## 七、Phase 3 推广模板（M2–M12 套用 M1 模式）

对任意模块 Mx（T1–T6）：
1. **T1 数据接入**：在 `bff/routes/modules.js` 对应 `real*Insight` 已具备只读层；缺表则新增 `store-inventory/migrations/NNN_*.sql`（仅增不改）。
2. **T2/T3 UI**：仿 `Analysis*Page` 在 `apps/admin-web/src/pages/ops/` 加子页（antd + SVG/CSS 图），注册 `App.tsx`/`menu.tsx`。
3. **T4 交互状态机**：复用 `usePeriodSwitch` 或按 docx 状态机在页内实现（并行查询/防抖/降级）。
4. **T5 写回**：`POST /api/sync {action,payload,rev}`（action 名见 4.3）→ 确认台 `confirm`（rev 校验）→ 店内消费者 `execute`/BFF `/apply` 三向合并写库。
5. **T6 验收**：该模块 E2E/单测；`verify-all` 零写库回归（只读层不得出现 INSERT/UPDATE/DELETE；脚本位置见第五节 Phase 4 门禁脚本位置提醒）。

## 八、前厅接口预留实现（美团切换，Phase 3A 落地）

**设计目标**：前厅 5 模块（会员营销/堂食收银/外卖平台/预订排队/顾客口碑）暂缓开发，但接口必须可"随时切回自营"——即 provider 从 `meituan` 切到 `self` 时，相关只读/写回路径自动启用，无需改代码。

**实现要点（全部已落地并通过冒烟）**：
1. 配置开关：`bff/.env` 的 `FRONT_OF_HOUSE_PROVIDER`（默认 `meituan`）。`bff/lib/provider.js` 读取并判断 `isSelf()`。
2. 只读预留路由：`bff/routes/reserved.js` 处理 `GET /api/{vip,pos,takeout,booking,review}`。
   - meituan：返回 `{code:200, data:{provider:'meituan', status:'reserved', switchable:true, module, note}, rev}`（只读、空操作）。
   - self：委托 `modules.js` 走真实只读层（`vipInsight`/`posInsight`/...），前厅数据照常可读。
3. 写回动作预留：`bff/routes/actions.js` 入队时对前厅 action（枚举见 `provider.js` 的 `FRONT_HOUSE_ACTIONS`，含 vip_*/pos_*/takeout_*/booking_*/review_*）标记 `front_house=true` / `pending_provider`。meituan 模式下 `confirm` 与 `apply`（BFF `/apply`）均返回 **423** 拦截，绝不写库；消费者侧 `store-node/consumer.js` 再有 `pending_provider` 兜底拦截。
4. 前端占位：`apps/admin-web/src/pages/ops/ReservedModulePage.tsx`（`/ops/reserved`）总览 5 个前厅模块的承接方/状态/可切换；菜单 `dinein`、`member` 分组叶子加 `reserved:true`（渲染"接口预留"Tag）。
5. 红线：`provider` 切换只改变"读哪层 + 是否允许消费动作"，reserved 路由与占位页始终只读/空操作，不引入写库副作用。

**切回自营步骤**：将 `FRONT_OF_HOUSE_PROVIDER` 改为 `self` 并重启 BFF → reserved 路由自动改走真实只读层，前厅 `confirm`/`apply` 不再拦截，写回动作经确认台正常三向合并写库。
