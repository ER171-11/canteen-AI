| 影响范围 | `bff/routes/settle.js`（新增）、`bff/data/settle_template.json`（新增）、`apps/admin-web/src/pages/SystemConfigPage.tsx`、`apps/admin-web/src/pages/inventory/settle/{template,html,pdf,data,export}.ts`、`apps/admin-web/src/pages/inventory/{SettleModal,SettleBatchModal,PayModal}.tsx` |

---

## 1. 背景

- 旧系统（单文件 HTML）把结算单模板存在**浏览器 localStorage** 的独立 key 里，与业务数据分离：
  `#stTpl*`（旧 HTML:615-628）表单、`renderSettleTplForm()` :5239、保存 :5253、恢复默认 :5269-5272。
- 替代模式下（`docs/迁移颗粒度规范.md`），设置页 19 项功能中 FP-SET-18/19 属设置类，
  与 FP-RECV-04/05/06/07（结算单全家桶 + 补付）构成同一个**业务闭环**：老板要打印付款单，就必须先能配抬头。
- 新版是多端架构（`admin-web` + Android + iOS），**没有**「每个老板只有一个浏览器」这个前提。

## 2. 决策

1. **存储位置**：模板存 BFF 独立文件 `bff/data/settle_template.json`，与业务快照（`snapshot.json`）**物理隔离**。
2. **访问方式**：仅新增一对端点，不扩张到业务域——
   - `GET /api/settle/template` → 当前模板（文件缺失时回落默认值，并回 `source: 'default'`）
   - `PUT /api/settle/template` → 保存模板，**仅 老板/店长** 可写（`auth.WRITE_ROLES`，显式排除 `只读`）
   - 其他方法一律 `405`。
3. **不走业务写链路**：模板**不是业务数据**，因此
   - 不进 `/api/actions` 审批队列（队列是给「会改变库存/资金事实」的动作用的）；
   - 不触发 `rev` 乐观锁、不参与三向合并、不进快照；
   - 只记一条审计（`audit.write({ note: 'settle_template.update' })`），审计失败不阻断主流程。
4. **输入白名单清洗**：`normalize()` 只保留 13 个已知字段（未知字段一律丢弃），
   缺省补默认值、显式空串保留（用户清空「抬头单位」是合法操作）；`subjects` 支持 `/ 、 , ，` 分隔。
5. **生成侧全在客户端**：结算单本身（打印 / CSV / 电子版 HTML / PDF）由 `admin-web` 生成
   （Blob / `Canvas` / `iframe` print），BFF 不生成任何单据——落实红线 ④「结算单是只读输出层，不写 DB」。

## 3. 为什么不是别的方案

| 备选 | 否决理由 |
|---|---|
| 继续用 localStorage（照搬旧版） | 多端不一致：老板在 admin-web 配的抬头，Android/iOS 上看不到；换机器即丢。且 localStorage 写入绕开角色校验与审计。 |
| 存进业务库（`data.config` 或 SQLite） | 模板是**打印外观配置**，不是业务事实。塞进业务库会污染 `rev`/合并/快照链路，且违反红线 ④ 的「不写 DB」。 |
| 存 `snapshot.json` 内部 | 快照是业务事实的可回滚副本；模板混进去会让快照语义变模糊，且回滚业务数据时连带回滚外观配置。 |
| 提交进 Git（仓库内置默认模板） | 无法按店修改；每改一次抬头就要发版。 |

## 4. 保了什么（意图层，不可让）

| 项 | 保障手段 |
|---|---|
| 模板字段全量对等（抬头/地址/电话/税号/用途/收款单位/开户行/账号/签字栏/页脚/明细列名） | `DEFAULT_TPL`（`settle.js`）与前端 `DEF_SETTLE_TPL` 逐字段对齐旧版 `DEF_SETTLE_TPL`（旧 HTML:2088-2095） |
| 恢复默认模板 | `SystemConfigPage.tsx` 的 `Popconfirm` + `resetTpl()`，二次确认且**不动任何业务数据** |
| 越权不可改 | `PUT` 校验角色，非老板/店长返回 `403` |
| 模板字段不成为注入面 | 字段进入 HTML/PDF 输出前一律经 `html.ts` 的 `esc()` 转义；新版本不引入任何 `innerHTML` 直写用户数据 |
| 参数不漂移 | 前端 `loadSettleTpl()` 读 BFF；`GET` 失败时回落本地默认值并给默认模板，**不静默显示空白单据** |


## 6. 副作用与遗留（需后续处理）

| # | 遗留 | 影响 | 建议 |
|---|---|---|---|
| 1 | 单文件存储，**无店/租户维度** | 多店时共用一份模板 | 需要多店时改为 `settle_template.{store}.json`，或并入配置中心 |
| 2 | 模板不参与快照/冷备份 | 文件丢失只能回默认 | 已用「恢复默认」兜底；长期应随 BFF 数据目录一并备份 |
| 3 | **未做人工视觉比对** | 新版 PDF 是零依赖自写引擎（`Canvas` 光栅化 → JPEG → PDF 字节流），门禁只证明「不崩、类型对」 | 按 T2 的复核方式，人工开箱比对旧版与新版的结算单版面后再转正式基线 |
| 4 | FP-RECV-06 与 FP-SET-18 为**同一实现的重复登记** | 统计口径上易被误算成两项工作量 | 已在两份基线中互相标注；统计时各记 1 项但不重复计工作量 |

## 7. 回档方案

- 逻辑回档：删除 `bff/data/settle_template.json` 即回到内置默认模板（`GET` 自动回落，带 `source: 'default'`）。
- 代码回档：本 ADR 不改变数据库结构与 `bff/store-node/*`（未触碰哈希基线文件），回档只需移除 `bff/routes/settle.js` 与其 `ROUTES` 注册。
- 无数据级回档成本：模板不进入业务库、快照与合并链路。
