## 1. 红线（来自 ADR-008 §4 / ADR-009 §4，违反即回退）

1. **红线① 唯一写入口**：任何写（新建/作废/折扣/收款）只走 `POST /api/actions` → 审批 → 消费器 → 快照回写；前端不复算、localStorage 不写。
2. **派生值不落库**：`欠款 = receivable − Σ payments.amount`、毛利率等一律实时算；快照 `sales[]` **不存**「欠款」字段（存下来必漂移，与欠账总表「汇总数是派生数据」同一教训）。
3. **口径唯一出口**：应收/实收/欠款三数只在 `bff/routes/report.js` 聚合，前端只渲染。
4. **高危留痕**：作废/回滚须审批留痕（本路径收款/作废沿用 ADR-004 进货单状态机：保留原单行、记作废人/时间/rev、rev 冲突返回 409）。

## 2. Phase A：只读解锁（低风险、不写快照、可立即验收）

> 原则：**防御性取值**，不在 `snapshot.json` 里造数据。当前 426 条真实 `sales[]` 无 `discount/receivable/payments`，
> 用「应收=amount、折扣=0、全额即收」的回退口径即可让 4 张卡真实出数，且未来真实数据进来时同一聚合自动生效。
> 这与 ADR-008 §7「不先上 ¥0 假卡」一致——我们是**按数据算出来为 0**，不是**写死 ¥0 MOCK**。

### A1. BFF 聚合（`bff/routes/report.js` 的 `deriveReport` 内）

在现有 `num/arr` 辅助函数旁新增取值与聚合（复用阶段 19 已验证的辅助函数）：

```js
// 防御性取值：真实快照缺字段时回退到 amount / 全额即收，避免造 MOCK
function receivableOf(s) { return s.receivable != null ? num(s.receivable) : num(s.amount); }
function discountOf(s)   { return s.discount != null ? num(s.discount) : 0; }
function paymentsOf(s) {
  if (Array.isArray(s.payments) && s.payments.length) return s.payments;
  const amt = num(s.amount);
  return amt ? [{ date: String(s.date || '').slice(0, 10), amount: amt }] : [];
}

// 区间与累计口径（沿用阶段 13 区间 [截止日-(r-1), 截止日]）
const receivableInRange = rangeRecs.reduce((a, s) => a + receivableOf(s), 0);   // FP-DASH-02 按单日期
const discountInRange   = rangeRecs.reduce((a, s) => a + discountOf(s), 0);     // FP-DASH-08
const receivedInRange   = rangeRecs.reduce((a, s) =>                           // FP-DASH-03 按收款日期
  a + paymentsOf(s).filter(p => p.date >= rangeStart && p.date <= rangeEnd)
                  .reduce((b, p) => b + num(p.amount), 0), 0);
const debtCumulative    = (data.sales || []).reduce((a, s) =>                  // FP-DASH-04 累计
  a + Math.max(0, receivableOf(s) - paymentsOf(s).reduce((b, p) => b + num(p.amount), 0)), 0);
```

在 `kpi[]` 追加 4 张卡（复用 FP-DASH-05 已落地的 `sub` 副标机制）：

```js
{ label: '应收合计',   value: '¥' + receivableInRange.toFixed(2),
  sub: '按单日期（本期）', delta: null },
{ label: '实收合计',   value: '¥' + receivedInRange.toFixed(2),
  sub: '按收款日期（本期）', delta: null },
{ label: '未收欠款',   value: '¥' + debtCumulative.toFixed(2),
  sub: debtCumulative > 0 ? '累计未收' : '已全部收讫', delta: null },
{ label: '折扣/抹零',  value: discountInRange > 0 ? '¥' + discountInRange.toFixed(2) : '¥0',
  sub: '本期（按单）', delta: null },
```

- `rangeStart/rangeEnd` 沿用 `deriveReport` 已有的阶段 13 区间变量，勿另造。
- 不新增任何前端 MOCK；`DashboardPage` KPI 卡片已支持 `sub` 渲染，新卡自动出现。

### A2. 前端（按需，通常零改动）

- `apps/admin-web/src/pages/DashboardPage.tsx` 的 KPI 卡片已按 `kpis[]` 动态渲染并支持 `sub`，A1 后即可见。
- 若需强调欠款>0，可在渲染处对 `key==='未收欠款' && 数值>0` 的 `sub` 标红（属锦上添花，非阻塞）。

## 3. Phase B：写类动作（FP-SALE-07/08/11，按 ADR-009 统一动作队列）

> 写路径**必须**走 ADR-009 §2.3 的「标准业务处理队列」，禁止在销售页另开写通道。
> 执行器对齐 ADR-004 进货单（`recv.update/void` 同型）：唯一写入口、动作注册、状态机、rev 乐观锁、越权不可写。

### B1. 动作类型注册（`bff/lib/algorithms/registry.js`）

- 新增 `sale.create` / `sale.void` / `sale.pay`（分次收款）等类型；**未注册即判 `need-manual`**（沿用既有规则）。
- 对应执行器文件建议 `bff/lib/algorithms/pos.js`（或 `sale.js`），与 `recv_import.js` 同构。

### B2. 消费器执行器（`bff/store-node/consumer.js` 调用新执行器）

- `sale.create`：向 `data.sales[]` 追加单（含 `receivable/discount/payments` 初始值）。
- `sale.void`：标记作废、保留原单行、记作废人/时间/rev（不物理删除）。
- `sale.pay`：**仅**向该单 `payments` 追加 `{ date, amount }`，不动 `receivable`（欠款=应收−Σpayments 实时派生）。
- rev 乐观锁先到先得，冲突返回 409（`confirm`）。

### B3. 审批 / 队列

- 提交即 `POST /api/actions` → 审批中心 → 消费器执行 → 快照回写（同 ADR-004）。
- 服务端 `auth.WRITE_ROLES` + `mayWriteActions` 为权威（越权 403）。

### B4. 前端

- **FP-SALE-07 销售单列表**：显示 应收 / 已收 / 欠款（欠款=应收−Σpayments，前端只渲染不计算，数据取自 `report` 或列表接口）。
- **FP-SALE-08 顶部 KPI**：复用 Phase A 的「本月应收（按单日期）/ 累计实收（按收款日期）」聚合，不另算。
- **FP-SALE-11 分次收款**：调 `sale.pay` 动作，UI 展示已收进度。

### B5. Phase B 验证

- 红线条：直接写 `sales[]`（绕过 `/api/actions`）返回 403；rev 冲突返回 409；作废保留原单行。
- 分次收款后断言：该单 `payments` 长度 +1、`欠款` 实时下降、` receivable` 不变。

### 7.3 与 §3/§2 的偏差登记（有意偏离，非静默）

1. **只读侧不另造端点口径**：FP-SALE-08 的顶部 KPI **复用** `report.js` 聚合（前端取 `report.kpi[]`），
   不在 `/api/admin/sales` 里再算一遍店级应收/实收/欠款 —— 守住红线③「口径唯一出口」。
2. **`payments` 空数组 ≠ 缺字段**（红线②的语义边界，实现时踩到并修正）：
   `payments: []` = 分文未收；**字段缺失**才回退「全额即收」。
   若把空数组也回退成全收讫，则「新建待收款单」会被读成已收清，欠款永远为 0。
3. **作废单从四个口径中剔除**：`sale.void` 后应收/实收/欠款/折扣均不再计入（否则作废单仍占用应收）。
   注意：既有「营收」KPI（`recordAmount`）**未加**作废过滤——保持既有行为不变，故存在作废单时
   「应收合计」会小于「营收」（有意为之，应收不应含作废单）。
4. **执行器不做 rev 校验**：与 `recv.*` 同构，rev 乐观锁由 `actions.js` `confirm`（409）与
   `consumer.js` 的 `baseRev` 三向合并承担（§B2 原文「rev 乐观锁先到先得」的实现位置即此两处）。
5. **`sale.create` 已注册但暂无 UI**：登记 Phase B1 要求的三个类型；admin-web 录单表单属
   FP-SALE-01/02（本指令未解锁），随 FP-SALE-12 一并做。

## 8. 坑位提醒

- **不要**在 `snapshot.json` 手写 `discount/receivable/payments` 假数据；用 §2 防御性取值即可。
- **不要**把「欠款」存进快照（派生值落库必漂移）。
- FP-DASH-08 折扣为 0 是真实状态，显示 `¥0` 即可，禁止为此造「本期无折扣」语义的假卡。
- 旧版 `payments` 是否含渠道/方式/备注尚未逐字段核对，落 `FP-SALE-11` 时回填并补差分用例（ADR-008 §7 遗留）。
