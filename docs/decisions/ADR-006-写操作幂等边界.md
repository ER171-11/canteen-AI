# ADR-006：写操作的事后幂等边界（「连点两下」不再产生两条动作）

- 日期：2026-09-29
- 状态：已实施
- 关联：ADR-002（去 Python 架构收敛）、ADR-003（进货单/写回口径）、ADR-004（进货单录入边界）、ADR-005（现场管理媒体与写回边界）
- 影响面：`bff/routes/actions.js`（写回队列唯一入口）、`bff/routes/run-tests.js`、`scripts/e2e-writeback.js`
- 触发：现场反馈「同一个动作连点两下 = 两条待审批 = 两笔入库」
- 备注：本 ADR 为**实现同步补记**（改动与本文同日落地）。按仓库「写类语义变更先写 ADR」的约定，顺序本应先文档后代码，此处如实标记，供审计识别。

---

## 1. 背景

全仓库红线②要求**所有写操作经 `POST /api/actions` 队列**（`bff/server.js:9`、`ci/redline_guard.sh`），
由「确认（queued → 待执行）→ 店内消费器执行 → 快照回写」两段式落地。

队列原有**一级幂等**（阶段 4）：同 `type + payload + operator` 哈希，若队列中已存在**仍在 OPEN（`queued`/`待执行`）**的动作，
则复用该动作并返回 `dedup:true`（`bff/routes/actions.js:84`）。

该规则漏掉了一类现场高频场景 —— **动作已经「已执行」之后又被提交**：

- 老板在审批中心/小程序上**连点两下**「保存/确认」；
- 客户端超时重试、队列消息重投。

此时第一个动作已离开 OPEN 状态，一级幂等不再命中 → **新建第二条 queued 动作** → 审批中心出现两条待审批 →
若都确认，就**落库两遍**（同一张进货单入两次库存）。这正是任务清单 §8.2.4 未复核项 3 登记、
阶段 6（`scripts/e2e-writeback.js` 第 12 步）实证复现的缺口。

---

## 2. 决策

### 2.1 增加第二级幂等：已执行动作的事后去重

`bff/routes/actions.js:72` 新增 `findExecutedDup(q, hash, nowMs)`：

- 命中条件：`hash` 相同（即 `type + payload + operator` 逐字节一致）**且** `status === '已执行'` **且** 处于时间窗口内；
- 命中后 `enqueue()` 返回 `{ action: 原动作, dedup: true, dedup_of: 'executed' }`（`bff/routes/actions.js:94-97`），
  **不新建动作**；`POST /api/actions` 响应回带 `dedup_of`（`bff/routes/actions.js:284`），
  `status` 直接回 `已执行` —— 前端连点的第二次看到的是「已完成」，不是一条新的待审批。

### 2.2 窗口 = 5 分钟（`EXECUTED_DEDUP_MS`，`bff/routes/actions.js:36`）

以「执行完成时刻」（`executed_at`）为基准向后推 5 分钟。取值权衡：

- **太短**：挡不住超时重试/消息重投（几秒到几分钟）。
- **太长**：会把「同一操作人过一会儿确实想再做一次同样的写操作」误判为重复
  ——例如 `stock.replenish {sku:"flour", qty:10}` 半小时后又补 10 kg，payload 逐字节相同。

5 分钟覆盖连点、重试、重投，而「payload 逐字节完全相同的两次独立写操作」在此窗口内极罕见；
超出窗口一律正常新建（**不做永久去重**）。

### 2.3 只对「已执行」生效

`已驳回` / `已过期` / `已回滚` **不参与**事后幂等，均可重新发起：

- 驳回后重新申请是正常诉求（驳回意味着这次没做，不应被锁死）；
- 回滚意味着动作被撤销，重做是合理的；
- 过期动作本就该被替代。

### 2.4 顺带修正：入队路径上的过期清扫不再丢失

`enqueue()` 原先在开头 `sweep(q)` 后丢弃了「是否有变更」的结果，仅在一级幂等命中分支再 sweep 一次（此时必为 `false`），
导致**过期清扫在入队路径上不落盘** —— 一条早已过期的 `queued` 动作在内存里仍是 OPEN，会让复投错误复用一条「应已过期」的动作。
现改为 `const dirty = sweep(q)` 并在提前返回前 `flush()`（`bff/routes/actions.js:85-86`）。

## 3. 为什么不是别的方案

| 备选方案 | 否决理由 |
|---|---|
| 接受为设计边界，仅在前端加提示 | 现场看到的是「两条待审批」，提示不能阻止**两笔入库**；写类风险的兜底必须落在服务端 |
| 永久去重（不限窗口） | 会把合法的重复业务操作（同原料再补同数量）永久屏蔽，现场无法自助绕开 |
| 只在客户端做幂等键（`request_id`） | 服务端仍需兜底（老版本 App、直连 API、重投）；且前端改动面比服务端大。**未做**，见 §7 |
| 让「已执行」的复投返回 409 报错 | 幂等的语义是「重复请求得到同一结果」，报错会让连点者以为保存失败，诱发第 3 次点击 |
| 用 `created_at` 而非 `executed_at` 作窗口基准 | 动作可能在队列里躺很久（等审批），窗口应覆盖「刚做完又被点」的真实场景 |

---

## 4. 保了什么

- **红线②不变**：仍然只有一个写入口 `POST /api/actions`，仍然两段式；本次只改「入队时是否新建」的判定。
- **连点两下 = 一条动作**：第二次请求返回 `dedup_of:"executed"` + 原 id + `已执行` 状态，零写入。
- **不误伤合法重复操作**：窗口外正常新建；换个单号/改个数量（payload 不同）即视为新操作。
- **驳回不锁死**：已驳回/已回滚/已过期都能重新发起。
- **可解释**：响应带 `dedup` / `dedup_of`，审计与前端都能区分「新建」「复用 OPEN」「复用已执行」。

## 7. 副作用与遗留

- **前端请求级幂等键（`request_id`）仍未做**：本 ADR 只覆盖「同内容重复提交」。若前端两次点击**各自生成单号/时间戳**导致 payload 不同，
  服务端指纹天然不同，仍会新建两条 —— 根治需前端传 `request_id` 并由服务端建索引（属前端 + 队列契约变更，另行决策）。
- **指纹包含 `operator`**：`POST /api/actions` 的 `operator` 取 `body.operator || 账号`。若前端一次传操作人、一次不传，
  同一操作的两次请求哈希不同，事后幂等不命中（属前端一致性问题）。
- **窗口可调**：`EXECUTED_DEDUP_MS` 是常量，若现场仍出现漏网重投，可上调；若出现误判重复，可下调。
- **回档**：`git revert` 本变更即回到「已执行后复投会新建动作」的旧行为，无数据迁移、历史动作不受影响（`hash` 字段本就存在）。
