通用软件架构范式 — 模块化组合式架构规范

================================================================
1. 设计哲学
================================================================

本架构的核心信念：
- 软件不是"建造"出来的，而是"组合"出来的。
- 任何业务系统都可以被拆解为：原子能力 → 功能模块 → 解决方案模板 → 运行时容器。
- 架构的目标不是写代码，而是定义"组合规则"。

三条铁律：
  铁律一：任何模块必须能脱离宿主独立运行、独立测试。
  铁律二：模块之间只通过"契约"通信，禁止隐式依赖。
  铁律三：所有业务逻辑必须可被序列化（JSON），可被非程序员修改。


================================================================
2. 五层架构模型
================================================================

  ┌─────────────────────────────────────────────┐
  │  L5  生态层 (Ecosystem)                       │
  │  所有模块的注册、发现、版本管理、市场分发       │
  ├─────────────────────────────────────────────┤
  │  L4  方案层 (Solution)                        │
  │  预组合的"套餐"，面向特定行业/场景             │
  ├─────────────────────────────────────────────┤
  │  L3  模块层 (Feature Module)                  │
  │  可独立交付的业务功能单元                       │
  ├─────────────────────────────────────────────┤
  │  L2  原子层 (Atomic Unit)                     │
  │  不可再分的最小能力单元                         │
  ├─────────────────────────────────────────────┤
  │  L1  内核层 (Kernel)                          │
  │  空壳运行时，提供模块加载、通信、生命周期管理    │
  └─────────────────────────────────────────────┘


================================================================
3. L1 内核层 (Kernel) — "操作系统"
================================================================

内核是唯一的"平台相关"部分，其余所有层均与平台无关。

内核职责（且仅限以下职责）：

  3.1 模块注册表 (Module Registry)
      - 维护已加载模块的清单
      - 提供模块发现与依赖解析
      - 接口：register(module), resolve(moduleId), list()

  3.2 通信总线 (Message Bus)
      - 模块间唯一合法的通信通道
      - 支持三种模式：
        a) 同步调用 (Request-Response)
        b) 异步事件 (Publish-Subscribe)
        c) 流式数据 (Stream)
      - 接口：emit(event, payload), on(event, handler), request(channel, payload)

  3.3 生命周期管理器 (Lifecycle Manager)
      - 控制模块的：加载 → 初始化 → 激活 → 休眠 → 卸载
      - 接口：load(moduleId), activate(moduleId), deactivate(moduleId), unload(moduleId)

  3.4 配置中心 (Config Center)
      - 全局配置与模块级配置的读取与热更新
      - 接口：get(key), set(key, value), watch(key, callback)

  3.5 权限网关 (Permission Gateway)
      - 统一的鉴权与授权拦截
      - 接口：can(actor, action, resource) → boolean

内核约束：
  - 内核代码量应控制在总代码量的 10% 以内。
  - 内核不包含任何业务逻辑。
  - 内核必须可被替换（如从 Web 环境切换到移动端或 CLI 环境）。


================================================================
4. L2 原子层 (Atomic Unit) — "标准零件"
================================================================

原子是系统中不可再分的最小能力单元。

  4.1 分类：
      a) UI 原子：一个纯展示/交互单元（按钮、输入框、图表）
      b) 逻辑原子：一个纯计算/处理函数（格式化、校验、转换）
      c) 服务原子：一个与外部系统交互的封装（HTTP调用、文件读写、消息推送）

  4.2 原子规格（必须全部满足）：
      - 零业务上下文：不知道自己在哪个系统、哪个页面、为谁服务。
      - 纯函数优先：相同输入必须产生相同输出（服务原子除外）。
      - 自包含：所有依赖通过参数注入，禁止隐式读取全局状态。
      - 自描述：必须导出一个 manifest 对象：
        {
          "id": "atom/supplier-select",
          "version": "1.0.0",
          "type": "ui",
          "inputs": [{ "name": "value", "type": "string", "required": false }],
          "outputs": [{ "name": "onChange", "type": "event" }],
          "dependencies": []
        }

  4.3 原子命名规范：
      - 格式：atom/{domain}/{name}
      - 示例：atom/finance/calculate-tax, atom/ui/supplier-select


================================================================
5. L3 模块层 (Feature Module) — "功能货架"
================================================================

模块是面向用户的、可独立交付的最小业务单元。

  5.1 模块规格（必须全部满足）：
      - 黑盒原则：对外只暴露 manifest 中声明的接口。
      - 自举能力：模块必须能自行注册路由、菜单、权限点。
      - 可插拔：移除模块后，宿主系统不报错、不崩溃。
      - 自带测试：每个模块必须包含完整的测试套件。

  5.2 模块标准目录：
      feature-{name}/
      ├── manifest.json          # 模块身份证（必须）
      ├── index.ts               # 唯一出口（必须）
      ├── components/            # 模块私有 UI
      ├── hooks/                 # 模块私有逻辑
      ├── services/              # 模块私有服务调用
      ├── atoms/                 # 模块私有原子（不对外暴露）
      ├── __tests__/             # 测试套件
      └── README.md              # 人类可读说明

  5.3 manifest.json 标准结构：
      {
        "id": "feature/reconciliation",
        "version": "1.0.0",
        "name": "对账管理",
        "description": "支持三单匹配、差异标记、账单生成",
        "dependencies": {
          "atoms": ["atom/finance/calculate-tax"],
          "modules": ["feature/supplier-management"]
        },
        "provides": {
          "routes": ["/reconciliation"],
          "menuItems": [{ "label": "对账管理", "path": "/reconciliation", "icon": "audit" }],
          "permissions": ["reconciliation:view", "reconciliation:export"],
          "events": ["reconciliation.completed", "reconciliation.failed"]
        },
        "config": {
          "defaultPageSize": 20,
          "autoMatch": true
        }
      }

  5.4 模块间通信规则：
      - 禁止：import { store } from '../other-module/store'
      - 禁止：直接调用其他模块的内部函数
      - 必须：通过内核通信总线 emit/on/request
      - 必须：通过 manifest 中声明的 events 进行事件通知


================================================================
6. L4 方案层 (Solution) — "行业套餐"
================================================================

方案是面向特定客户群体的、预组合好的模块集合。

  6.1 方案的本质：
      - 一份 JSON 配置文件（solution.json）
      - 描述了：哪些模块、什么版本、如何连线、默认配置

  6.2 solution.json 标准结构：
      {
        "id": "solution/ecommerce-backend",
        "name": "电商后台管理",
        "version": "1.0.0",
        "modules": [
          { "id": "feature/user-management", "version": "^1.0.0" },
          { "id": "feature/order-management", "version": "^1.0.0" },
          { "id": "feature/reconciliation", "version": "^1.0.0" }
        ],
        "wiring": [
          {
            "from": "feature/order-management:order.completed",
            "to": "feature/reconciliation:triggerMatch"
          }
        ],
        "globalConfig": {
          "theme": "default",
          "locale": "zh-CN"
        }
      }

  6.3 方案的可变性：
      - 客户购买方案后，可以在 UI 上进行：
        a) 启用/禁用模块
        b) 修改模块配置
        c) 调整模块间的连线
        d) 替换某个模块为自定义版本
      - 所有修改最终都体现为 solution.json 的变更


================================================================
7. L5 生态层 (Ecosystem) — "应用市场"
================================================================

生态层是跨项目、跨团队、甚至跨公司的模块流通基础设施。

  7.1 核心能力：
      - 模块注册中心：发布、搜索、版本管理
      - 依赖解析器：自动计算模块间的依赖树
      - 兼容性检查：验证模块间的接口契约是否兼容
      - 质量评分：基于测试覆盖率、使用量、缺陷率等指标

  7.2 模块生命周期：
      开发 → 测试 → 发布(Alpha) → 验证(Beta) → 稳定(Stable) → 废弃(Deprecated)

  7.3 版本策略：
      - 遵循语义化版本 (SemVer)
      - manifest 中的 dependencies 使用范围匹配（如 "^1.0.0"）
      - 内核负责在运行时解析并加载兼容版本


================================================================
8. 跨项目复用规则
================================================================

本架构适用于任何项目，无论前端、后端、CLI 或移动端。

  8.1 复用判定标准：
      - 一个模块能否被另一个项目直接使用？
        → 检查：它是否依赖了宿主项目的特定代码？
        → 如果依赖了，说明它还不是真正的模块，需要继续解耦。

  8.2 跨项目复用的三种方式：
      a) 源码级复用：模块以 monorepo 中的 package 形式存在
      b) 二进制级复用：模块编译为 npm 包 / Docker 镜像
      c) 远程级复用：模块部署为微服务，通过 API 调用

  8.3 跨项目通信：
      - 同进程：使用内核通信总线
      - 跨进程：使用标准化 API 网关（REST/gRPC）
      - 跨系统：使用事件总线（Kafka/RabbitMQ）+ 统一消息格式


================================================================
9. AI 执行指令集
================================================================

当 AI 参与本架构下的开发时，必须遵循以下决策树：

  9.1 用户说"新建功能"：
      → 创建 feature 目录 + manifest.json + index.ts
      → 识别所需原子，优先从生态层查找已有原子
      → 编写测试套件
      → 注册到模块注册表

  9.2 用户说"新建原子能力"：
      → 创建 atom 目录 + manifest
      → 确保零业务上下文、纯函数、自包含
      → 编写单元测试，覆盖率 > 90%

  9.3 用户说"组装系统"：
      → 生成 solution.json
      → 从注册表中拉取所需模块
      → 配置 wiring（模块间连线）
      → 运行兼容性检查

  9.4 用户说"解耦/重构"：
      → 检查模块是否违反黑盒原则
      → 检查是否存在跨模块直接引用
      → 将隐式依赖改为通过通信总线显式通信
      → 更新 manifest

  9.5 用户说"测试"：
      → 原子层：单元测试，覆盖率 > 90%
      → 模块层：集成测试 + 契约测试
      → 方案层：E2E 测试，覆盖所有 wiring 路径
      → 生态层：兼容性矩阵测试


================================================================
10. 关键术语速查
================================================================

  Kernel        内核，空壳运行时，提供基础设施
  Atom          原子，不可再分的最小能力单元
  Feature       模块，可独立交付的业务功能单元
  Solution      方案，预组合的模块集合（套餐）
  Ecosystem     生态，模块的注册、发现与分发平台
  Manifest      清单，模块的身份证与契约声明
  Wiring        连线，模块间的通信与数据流配置
  Contract      契约，模块对外承诺的输入/输出规范
  Lifecycle     生命周期，模块从加载到卸载的完整状态机
  SemVer        语义化版本，主版本.次版本.补丁版本
