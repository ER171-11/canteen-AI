# 决策分析定式（用户可感知决策法）

- 版本：v1.0
- 日期：2026-10-29
- 来源：从 W3-01（手工校准）、W4（高危三件套）的实际分析过程中抽象
- 定位：**分析定式**，不是决策记录。决策结论仍写进 ADR（如 `ADR-013-高危写与手工校准收口.md`）
- 触发词：「用决策定式分析 X」「按定式看」「这跟 D3/D4 一样分析一下」

---

## 0. 指令块（可直接粘贴到任意对话开头）

```text
请按「用户可感知决策定式」分析 <问题>，不要先给方案。严格输出以下 7 段：

0 划范围：这次只约束哪一类操作（手动改 / 自动流程 / 一次性迁移）？明确不涉及什么，
  防止把系统自动行为混进来。
1 核现状：逐端列出用户实际从哪个界面点得到（后台 / 移动端 / 桌面 / API）；
  表单里真实能改哪些字段；严格区分「后端支持」与「前端已露出」。
2 列路径：找出所有看起来能完成同一件事的路径，标注哪条是用户真能用的、
  哪条只是理论上存在。
3 比差异：按 8 个维度对比——入口与操作成本 / 操作语义 / 是否留痕 / 是否持久 /
  跨端一致 / 失败表现 / 可逆性 / 权限审批。
4 抓假绿：指出哪条路径「看着成功、实际会被重算或覆盖」，给出具体触发点与判据。
5 定分工：多数情况不是二选一，而是各管一件事。写清 A 场景走哪条、B 场景走哪条，
  并显式写下「禁止用 X 做 Y」。
6 写验收：每条验收必须是用户可感知的结果（数字 / 页面 / 流水），
  并包含「再操作一次是否保持」的回归项。禁止用「单测通过」当验收。
7 抽决策点：只列必须人拍板的，编号（D1/D2…）+ 推荐值 + 代价 / 风险。

硬约束：
- 不许用「后端支持所以能做」当结论；
- 不许用「代码跑通」当用户验收；
- 不许忽略「下一次自动流程会不会覆盖」；
- 每条现状结论尽量带文件路径或界面位置，不凭印象。
最后再问我要不要落地实现。
```

## 1. 适用与不适用

| 适用 | 不适用 |
|---|---|
| 同一件事有多条实现路径，要选型 | 纯功能新增、只有一条路 |
| 已有部分实现，卡面表述可能失真 | 纯 UI 样式调整 |
| 高危 / 不可逆操作，要先想清用户后果 | 纯文档措辞 |
| 需求与系统现状可能冲突，需先核对 | 已经有明确 ADR 且无歧义 |

## 2. 七步定式（展开）

### 第 0 步 · 划范围

**要回答**：这个问题约束的是哪一类操作？

- 手动改（人主动录入/校准）
- 自动流程（进货入库、销售扣料、系统重算）
- 一次性迁移（导入、重置、清空）

**为什么**：范围不划，分析会把「系统自动行为」和「人工决策」混在一起，结论必然错位。

> 案例：D3 一开始被理解成「两条都能改库存的路径二选一」，划清范围后才发现只有一条是用户能手工触达的。

### 第 1 步 · 核现状（禁用想象）

**要回答**：用户**实际**从哪个界面点得到？表单里**真实**能改哪些字段？

必须逐端核：
- 后台 admin-web
- 移动端 / Android
- 桌面壳
- 裸 API

**关键区分**：
- 「后端支持这个字段」≠「前端露出了这个入口」
- 「有执行器」≠「用户能用」

> 案例：`ing.upsert` 后端能写 `stock/avg`，但后台原料编辑表单**没有这两个输入框**（`StockPage.tsx:528-626`）。若只看后端，会得出完全相反的结论。

### 第 2 步 · 列路径

把所有「看起来都能完成同一件事」的路径列全，并打标：

| 标记 | 含义 |
|---|---|
| ✅ 用户真能用 | 有界面入口，点了有效 |
| 🟡 部分可用 | 有入口但字段不全 / 只覆盖一部分场景 |
| ⚪ 理论存在 | 只有后端能力或脚本，用户摸不到 |
| ⛔ 旁路 | 能写但绕开了审批/队列（红线风险） |

> 案例：改库存 = `stock.count`（✅ 移动端）+ `ing.upsert`（⚪ 后端有、前端无）+ `push`（⛔ 旁路）。

### 第 3 步 · 比差异（8 维）

不要只说「A 比 B 好」，要按用户能感知的维度逐项对比：

| # | 维度 | 要问的问题 |
|---|---|---|
| 1 | 入口与操作成本 | 用户在哪个页面、几步能到？ |
| 2 | 操作语义 | 绝对值 / 增量 / 字段编辑？用户怎么理解？ |
| 3 | 是否留痕 | 台账、审计、差异表能不能看到？ |
| 4 | **是否持久** | 下一次自动流程会不会覆盖？ |
| 5 | 跨端一致 | 后台改完，手机看到的是同一个数吗？ |
| 6 | 失败表现 | 失败是显式报错，还是静默成功？ |
| 7 | 可逆性 | 错了能不能撤回？靠什么撤回？ |
| 8 | 权限审批 | 谁能做？要不要确认？ |

**第 4 维（持久）是最容易被忽略、也最致命的。**

### 第 4 步 · 抓假绿

**要回答**：哪条路径「看着成功、实际会被冲掉」？

常见触发点：
- 系统有**全量重算**（如 `rebuildStock` 从流水重放）
- 缓存/快照覆盖
- 异步队列没执行，前端却提示成功
- 只改了展示字段，没写账务流水

**判据（两条都要问）**：
1. 改完之后，下一次自动流程会不会把它覆盖？
2. 这次改动有没有留下可追溯的流水/审计？

> 案例：`ing.upsert` 直改 `avg` → 下一次 `rebuildStock` 先清零再重放 → 改动消失；且无流水 → 双重假绿。

### 第 5 步 · 定分工（不是二选一）

多数情况的正确答案是**各管一件事**，而不是砍掉一条：

- A 场景（盘点/对账）→ 路径 1
- B 场景（主数据维护）→ 路径 2
- C 场景（手工校准）→ 复用 A 的账务口径，但独立入口

并显式写下禁止项：

> 「禁止用 `ing.upsert` 改存量 `stock/avg`」
> 「禁止用 `push` 做导入」
> 「禁止把库存/均价加进档案编辑表单」

### 第 6 步 · 写验收（用户可感知）

验收必须能被用户看见：

- 数字变了（库存总值不为 0）
- 页面多了一行（台账出现「手工调整」）
- 提示语明确（“将丢弃 426 条销售”）

并加一条**回归验收**：

> 「再做一次触发自动流程的操作，值是否还在？」

禁止用「单测通过」「接口返回 200」当用户验收。

### 第 7 步 · 抽决策点

只把**必须人拍板**的抽出来，每条给：

- 编号（D1 / D2…，便于跨对话引用）
- 推荐值
- 代价 / 风险（选另一个会怎样）
- 是否阻塞后续（哪几张卡依赖它）

不要把「可以自己查清的事实」包装成决策点。

## 4. 反模式清单（见到就停）

| 反模式 | 为什么错 |
|---|---|
| 「后端支持，所以能做」 | 前端没露出来，用户根本用不到 |
| 「单测过了，所以验收完成」 | 单测不证明用户看到正确结果 |
| 「两个入口都能改，选一个砍掉」 | 多数是两个不同场景，砍掉会造成缺口 |
| 「改完立刻看到新值，说明生效了」 | 可能只是前端乐观更新/内存值，下一次重算就没了 |
| 「提示成功，就是成功了」 | 队列可能没执行（`CANTEEN_LOCAL_APPLY` 未开时动作会停在待执行） |
| 「重置就是回到初始状态」 | 要看基线里到底有什么、会丢什么 |
| 「清空数据 = 删表」 | 派生数据会从源数据重算回来（只清 `logs` 保留 `recv`，库存会复活） |

## 5. 精简示例（D3 回放）

**问题**：W3-01 要手工校准库存/均价，走哪条路？

- **0 范围**：只约束「人工改账面」，不含进货入库/销售扣料/重算。
- **1 现状**：后台编辑表单无库存/均价字段；移动端有「盘点改账」走 `stock.count`，但不含均价。
- **2 路径**：`stock.count`（✅ 移动端）、`ing.upsert`（⚪ 后端有、前端无）、`push`（⛔ 旁路）。
- **3 差异**：`stock.count` 留痕、持久、有差异表；`ing.upsert` 无痕、会被重算覆盖。
- **4 假绿**：`ing.upsert` 改完下一次 `rebuildStock` 清零重放 → 消失。
- **5 分工**：盘点 → `stock.count`；主数据 → `ing.upsert`；手工校准 → 独立入口但复用「手工调整」流水。
- **6 验收**：台账出现「手工调整」、库存总值不为 0、再进货后值仍在。
- **7 决策点**：入口形态（A 独立弹窗 / B 塞进编辑表单）→ 推荐 A。
