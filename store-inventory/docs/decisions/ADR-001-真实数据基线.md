# ADR-001: 采用真实采购单作为数据基线

- 状态: 已采纳
- 创建时间: 2026-09-12
- 决策者: 项目负责人

## 背景
原进销存系统内置虚构演示数据（文昌光鸡、鸭肉等56种原料，6张假采购单，7张假销售单，6条假报价），与餐厅真实经营数据不符，会误导经营决策。

## 可选方案
- 方案A: 保留演示数据，用户自行删除替换
- 方案B: 用真实采购单(海南菜篮子实业)替换演示数据，销售/报价/配方留空待录入

## 决策
选择方案B。用真实采购单的84行实收明细建立原料目录和采购单基线；菜品目录保留保本测算的86道（真实菜单）；销售单、外部报价、配方(BOM)因暂无真实数据置空。

## 后果
- 优点: 系统启动即呈现真实经营数据，无需用户清理演示数据
- 缺点: 销售/毛利/比价模块初始为空，需开业后逐步录入
- AI注意事项: 禁止恢复任何演示数据；销售单为空属正常状态，不要为演示效果填充虚构数据

# ADR-002: LS_KEY 版本升级机制

- 状态: 已采纳
- 创建时间: 2026-09-12
- 决策者: 项目负责人

## 背景
修改数据结构后，浏览器 localStorage 中旧版本数据可能导致兼容问题。

## 可选方案
- 方案A: 沿用原 key，靠兼容代码迁移
- 方案B: 升级 LS_KEY 版本号(v1→v2)，强制丢弃旧数据重新初始化

## 决策
选择方案B。每次数据结构不兼容变更时升级 LS_KEY 版本号，简单可靠。

## 后果
- 优点: 无迁移代码复杂度，避免脏数据
- 缺点: 用户旧数据丢失（但旧数据是演示数据，无价值）
- AI注意事项: 修改 seedDB 数据结构时必须同步升级 LS_KEY

# ADR-003: 外接比价采用「脚本抓价 + 文件导入」的离线流水线

- 状态: 已采纳
- 创建时间: 2026-09-13
- 决策者: 项目负责人

## 背景
ADR-001 决策后 `DB.quotes` 为空，外部报价需人工逐条查询录入（74 种原料）。`脚本文本.txt` 已提供 1688 `item_search` API 调用示例，用户要求「保留原有功能的同时接入更自动化的『一键比价』，且通过脚本实现」。

## 可选方案
- 方案A: 前端直接 fetch 1688 接口
- 方案B: 引入后端服务代理调用接口
- 方案C: 外部 Python 脚本抓价 + JSON 文件契约与前端解耦（离线流水线）

## 决策
选择方案C。
- 前端只做「导出待比价任务」与「导入比价结果」，不发起跨域请求、不持有 API 密钥
- 脚本产出与手工录入完全同构的 `DB.quotes` 记录，`renderPrice()` 等渲染函数零改动
- 导入为**追加 + 去重**，不删除/覆盖既有报价，`ingId` 未命中/价格非法/日期非法分别计数提示

## 后果
- 优点: 与现有「单 HTML + localStorage + 无后端」架构完全兼容；无 CORS 问题；密钥只存本地；手工比价通道完整保留、两条路径互不干扰；`DB.quotes` 只参与比价展示，不污染库存与配方成本
- 缺点: 多了一步「把任务文件放进脚本目录再跑」的人工操作；脚本依赖第三方接口的付费/免费 Key；1688 报价含运费/规格口径不一，仍需人工判断
- AI注意事项:
  - **「外部报价可由脚本导入」是既有能力，手工录入不再是唯一路径**，但手工路径必须保留
  - 一键通道只允许写 `DB.quotes`，禁止写 `DB.logs`/`DB.ings.stock`/`DB.ings.avg`/`DB.rec`
  - 文件契约（`panda-quote-task` / `panda-quote-result`）变更须前后端 + 脚本三处同步
  - 换算率 ≠ 1 的原料默认跳过，禁止在脚本里自动推断跨单位价格
  - 不因本功能升级 `LS_KEY`

# ADR-004: 抓价引擎由「开放平台接口」扩展为「接口 + Selenium 浏览器」双引擎

- 状态: 已采纳
- 创建时间: 2026-09-13
- 决策者: 项目负责人

## 背景
ADR-003 选定「外部脚本 + JSON 契约」的离线流水线后，`fetch_quotes.py` 走的是第三方聚合接口（onebound）的 1688 `item_search`。实际使用中用户反馈「1688 开放平台上的功能不符合预期」，希望改为 Selenium 模拟真实浏览器行为直接抓取 `s.1688.com` 搜索结果，节奏控制在每次操作约 2.5 秒。

## 可选方案
- 方案A: 直接改写 `fetch_quotes.py`，接口方案整体替换为 Selenium
- 方案B: 用 Selenium 重写一套独立脚本，重复实现任务解析与结果写出
- 方案C: 新增独立浏览器引擎脚本，**复用同一份任务/结果契约与写出逻辑**，与接口引擎并存

## 决策
选择方案C。
- 新增 `比价脚本/fetch_quotes_selenium.py`，直接 `import fetch_quotes` 复用 `find_task_file`/`load_task`/`write_json`/`write_excel`，**不复制任何契约代码**
- 两引擎产出结构完全相同的 `比价结果.json`，前端 `importQuoteResult()` 与 `DB.quotes` 结构零改动，仅 `source` 标签区分来源
- 保留接口引擎：接口可用时它更快（无需浏览器、无 DOM 改版风险），浏览器引擎作为接口不可用/数据不符预期时的替代通道
- 浏览器引擎采用持久化 Chrome 用户目录（`chrome_profile/`）承载登录态，反自动化指纹 + 2.5s 节奏控制，遇登录/滑块暂停并等待人工处理

## 后果
- 优点: 前端零改动即可切换数据源；两引擎可混用（同一批任务跑两次、不同来源追加进 `DB.quotes`，靠「原料+来源+价格」去重）；接口受限时业务不中断
- 缺点: 浏览器引擎单次耗时长（2.5s × 操作数），DOM 选择器依赖 1688 前端结构、存在改版失效风险；`chrome_profile/` 含个人登录凭据，需注意不外发
- AI注意事项:
  - **两个引擎必须保持结果契约一致**；契约变更须前端 + 两个脚本三处同步
  - `chrome_profile/`、`debug/` 是运行时数据，**禁止**提交/外发；**禁止**把 `delay` 降到 1s 以下；**禁止**试图自动化绕过滑块验证码
  - 选择器失效时只改 `fetch_quotes_selenium.py` 顶部的 `CARD_SEL`/`TITLE_SEL`/`PRICE_SEL` 等常量，不得改动契约字段
  - 不因本功能升级 `LS_KEY`；本次前端 HTML 零改动
