# ADR-009：服务端快照形态与销售/采购录入职责边界

- 日期：2026-10-12
- 状态：**已定案**（批准人：William，2026-10-12 签署）
- 关联：ADR-004（进货单录入边界，状态机对齐基准）、ADR-006（写操作幂等边界）、ADR-008（销售应收模型按单日期）
- 影响面：`bff/routes/snapshot.js`（快照读取/回滚端点）、`apps/admin-web` 客户端缓存层（localStorage 热备份）、销售收银与采购管理录入模块、`bff/lib/algorithms/registry.js`（新动作类型注册）
- 触发：欠账总表「执行前置依赖」三项一次解除——①「服务端快照」形态、②采购单/销售单同名职责边界、③双机同步四件套是否废弃
- 备注：本 ADR 是**纯口径/边界决策**，不落代码；落地随 `FP-SET-07/10`、`FP-PO-01/02`、`FP-SALE-*` 各卡片推进。

---

## 1. 背景

- 服务端快照现状（`bff/routes/snapshot.js`）：只有**一份最新快照** `data/snapshot.json`
  （`POST /api/snapshot/push` 覆盖写、`GET /api/snapshot/latest` 只读最新），
  **无历史列表、无回滚端点**。故 `FP-SET-07`（手动打快照备份）、`FP-SET-10`（快照列表查看与回滚）均 ⬜。
- 采购单（FP-PO-01/02）与销售单（FP-SALE-01/12/13）的录入边界未定，
  与 ADR-004 已解决的「进货单在店内录还是云端录」是**同一类问题**，未定不得动代码。
- 双机同步四件套（FP-SET-05/06/08/09：同步地址配置 / 立即同步 / 以数据库为准 / 以本机为准）
  在新版中心化 BFF/SaaS 架构下**已无存在意义**（`FP-设置.md` FP-SET-05 处置列：
  「新版为中心化 BFF/SaaS，无 P2P 双机同步」），但按规范 §3 ⚰️ 废弃需业务批准人签字方可转状态。

## 2. 决策

### 2.1 服务端快照形态：服务端主存 + 客户端 localStorage 热备份

- **服务端主存（单一数据源）**：`data/snapshot.json` 仍是权威快照，
  在既有 `push`/`latest` 之上，`FP-SET-07/10` 落地时扩展为**带历史列表**的服务端快照存储与读取。
- **客户端 localStorage 热备份（只读体验层）**：admin-web 把最近一次成功读取的服务端快照
  在 `localStorage` 落一份副本，**仅用于客户端断网时仍可读取上次数据**，不参与任何写路径。
  - 它是**只读缓存**，不是第二数据源；任何写操作仍只走服务端队列（红线 ①）。
  - **过期自动清理**：副本带时间戳，超期即失效删除，避免陈旧数据被误当成「最新」。
- 定位一句话：**服务端是「真」，localStorage 是「断网可读的暖备」，且会过期**。

### 2.2 回滚操作需运营管理员手动审批

- 快照回滚（`FP-SET-10`）属**高危写**：回滚不是普通动作，会让整库回到历史时点。
- 决策：回滚动作**必须经运营管理员手动审批**后方可执行，流程 = 建议动作入队 → 审批 → 消费器执行，
  **并全程留痕**（谁在何时从哪个 rev 回滚到哪个 rev）。这是「回滚高危，须留痕」的既有一致要求，
  也是 ADR-006 事后幂等、ADR-004 唯一写入口的自然延伸。

### 2.3 职责边界：销售端录销售单、采购端录采购单

- **销售单由销售端录入，采购单由采购端录入，不跨域代录**——各自有明确归属页面，杜绝「采购页顺手录张销售单」这类边界模糊。
- **统一走标准业务处理队列**：两类单据的写操作（新建/编辑/作废/导入/收款）一律
  「建议动作 → `POST /api/actions` → 审批 → 消费器执行 → 快照回写」，**不设任何特殊分流、不新增第二条写通道**。
- **与现有「进货单」的职责边界和状态机保持完全一致**（对齐 ADR-004），具体对齐项：
  - **唯一写入口**：与进货单同——云端 admin-web 为唯一写入口，现场电脑用局域网打开同一套 admin-web；
  - **动作类型注册**：采购/销售各自新增 `order.*` / `sale.*` 动作类型并在 `registry.js` 注册（未注册即判 `need-manual`）；
  - **状态机一致**：状态留痕、作废不物理删除（保留原单行、记作废人/时间/rev）、
    `rev` 乐观锁先到先得、冲突 `confirm` 返回 409 —— 与进货单 `recv.update/void` 同型；
  - **越权不可写**：服务端 `auth.WRITE_ROLES` + `mayWriteActions` 为权威。
- 目的：**避免产生两套逻辑**——采购/销售/进货三域共用同一套队列、幂等、审批、状态机，
  新增一域只是「新增动作类型 + 执行器」，而不是「再复制一套写链路」。

### 2.4 双机同步四件套：确认废弃，不再开发与维护

- `FP-SET-05 / 06 / 08 / 09`（同步地址配置 / 立即同步 / 以数据库为准 / 以本机为准）**确认 ⚰️ 废弃**。
- 理由：当前架构已全面转向中心化 BFF/SaaS，单一数据源在服务端，「本机 ↔ 本地 SQLite」的双机同步
  已被 §2.1 的「服务端主存 + 客户端热备份」取代，四件套不再开发、不再维护。
- 签署：本项由业务批准人 **William（2026-10-12）** 签字确认，`FP-设置.md` 四行状态由 ⬜ 转 ⚰️。

## 3. 为什么不是别的方案

| 备选 | 否决理由 |
|---|---|
| 快照只留在 localStorage（不建服务端历史） | 违背「单一数据源在服务端」，多端/换机器即丢；回滚也无权威基线可回 |
| 服务端快照但不做客户端热备份 | 断网时白屏/无数据可读，现场体验退步；localStorage 热备份成本极低、收益明确 |
| 回滚做成「一键直回、免审批」 | 整库回退属不可逆高危（FP-设置.md FP-SET-10「回滚高危，须留痕」），必须人审 |
| 销售/采购各自开一条写链路（特殊分流） | 会再造一套队列/幂等/审批/状态机，正是「两套逻辑」；ADR-004 已证明唯一入口是底线 |
| 双机同步四件套「保留为可选项」 | 中心化架构下它们是死代码与死配置，保留只增加维护面与误触风险；应显式废弃 |

## 4. 保了什么

- **红线 ① 唯一写入口不破**：快照、回滚、采购/销售录入全部仍经 `POST /api/actions`；localStorage 只读。
- **单一数据源不漂移**：服务端 `snapshot.json` 为「真」，客户端副本过期即弃。
- **高危有人审**：回滚必须运营管理员手动审批并留痕。
- **三域一套状态机**：采购/销售与进货单（ADR-004）状态机、幂等、rev 完全同构，无第二套逻辑。

## 5. 落地清单与实施状态

本 ADR 为决策层，落地分属各卡片（状态在其卡片登记），此处登记「边界已解除」：

| 项 | 内容 | 关联卡片 |
|---|---|---|
| 服务端快照形态 | 服务端主存 + localStorage 热备份（过期清理） | FP-SET-07/10 |
| 回滚审批 | 运营管理员手动审批 + 留痕 | FP-SET-10 |

| 销售录入边界 | 销售端录销售单，统一队列，与进货单同状态机 | FP-SALE-01/12/13 等 |
| 双机同步废弃 | FP-SET-05/06/08/09 → ⚰️（批准人 William） | 见 `FP-设置.md` |

## 6. 如何验证

- 决策层不跑测试；落地后按各卡片验证。关键的边界自证：
  - 快照读路径：断网时 admin-web 仍能读上次快照（localStorage 热备份生效），且过期副本不再出现；
  - 回滚：非运营管理员无法触发回滚；回滚全程留痕；
  - 采购/销售录入：提交后进同一审批中心队列，`rev` 冲突返回 409，作废留痕不物理删。

## 7. 副作用与遗留

- 客户端 localStorage 热备份的**过期阈值、配额上限**（避免撑爆浏览器配额）在 FP-SET-07 落地时定值；
  需沿用 `usePeriodSwitch.ts` 已有的「catch 忽略配额错误」兜底手法。
- 回滚执行器需明确「回滚到哪个 rev」的取数（服务端历史列表），并纳入 `ci/redline_baseline.sha256` 哈希基线评估，
  与 ADR-004 §7 第 7 项「有意偏离须登记」同一要求。
- 销售端移动端 POS 现有「点菜 + 全额收款」子集（FP-SALE-01/02）与 admin-web 销售页的关系
  ——收银子集是否合并进 admin-web 销售页、还是保留移动端——本 ADR 不定，留待 FP-SALE-01 落地时在 ADR-008 口径下细化。
