# ADR-005：现场管理媒体的存储边界与写回路径

- 日期：2026-09-29
- 状态：已实施
- 关联：ADR-002（去 Python 架构收敛）、ADR-003（进货单/写回口径）、ADR-004（进货单录入边界）
- 影响面：`bff/`（新路由与算法）、`store-inventory/migrations/`（003/004）、`kmp-shared/`、`apps/android-app/`、`apps/admin-web/`
- 触发：现场管理四块能力（A 品控 / B 桌态 / C 巡检 / D 水印相机）落地，涉及「照片存哪」「写操作走哪」「没配置怎么办」三类系统性抉择

---

## 1. 背景

现场管理四块能力都要处理**照片**，但两类照片的性质完全不同：

- **A 品控**：后厨饺子出锅后拍照，AI 识别缺陷并判定绿/红/橙。后台（admin-web）需要看**不合格大图**，因此图片必须能在另一台设备上打开 → 需要可公网/内网寻址的存储。
- **C 闭店巡检**：50 个点位拍照留证，用户已明确「照片**只存在手机本地**，服务器只记已拍/未拍」。

同时全仓库有两条既有红线（`bff/server.js:9`、`ci/redline_guard.sh`）：

1. **图片 base64 只在内存用，响应后销毁**，不落盘、不入库、不进 `store-node` 快照；
2. **所有写操作必须经 `POST /api/actions` 队列**（`ConfirmGateway` 两段式确认），不得新开旁路直接写库。

任何新能力都必须在这两条红线内落地。本 ADR 记录四块能力如何满足这两条红线，以及派生出的关键约束。

---

## 2. 决策

### 2.1 品控照片：走外部对象存储，BFF 只签 URL，DB 只存引用

- App 拍照后**直传对象存储**（S3 兼容：OSS/COS/MinIO 均可），BFF **不接触图片字节**。
- BFF 提供三个端点（`bff/routes/qc_media.js`）：
  - `GET /api/qc/media/status`（`:88`）→ 返回是否已配置及缺失变量，供前端决定是否显示「图片不可用」；
  - `POST /api/qc/media/presign`（`:94`）→ 签发 `PUT` 上传 URL（`objstore.presignPut`，`bff/lib/objstore.js:210`）；
  - `POST /api/qc/media/sign`（`:162`）→ 批量签发读取 URL（`objstore.presignGet`，`:218`），供 admin-web 私有桶读图。
- 预签名**零依赖自研**（手写 AWS SigV4，`bff/lib/objstore.js`），不引入 AWS/OSS SDK，守住「BFF 零依赖」。
- 数据库只存 `photo_url` / `photo_key` 两个**引用字符串**（迁移 `store-inventory/migrations/003_qc_media.sql`），不存图片本体。
- **刻意不设 commit 端点**：预签名直传后，key/URL 由 App 随品控动作一起提交，落库统一走 `POST /api/actions`（见 `bff/routes/qc_media.js:14-16` 注释），少一次往返、少一个中间态。

### 2.2 巡检照片：只存手机本地，服务器只存状态

- 巡检照片由端侧 `PhotoStore` 落盘到应用私有目录（`apps/android-app/.../media/PhotoStore.kt`），服务器**无任何图片列**。
- 服务端只记录「该点位是否已拍照」（`inspection_records`，迁移 `004_inspection.sql`）。
- 巡检算法（`bff/lib/algorithms/inspection.js`）内置 `hasImagePayload`（`:74`）守卫：请求体若出现图片 base64，直接**丢弃该字段并置 `photo_local_only=1`**，不报错、不影响状态落库。

### 2.3 写回：全部走 `/api/actions` 唯一入口

- 品控结论 `qc.record`、强制放行 `qc.force_pass`（注册于 `bff/lib/algorithms/registry.js:77,80`），巡检记录/指派（`inspection.js` 的 `recordInspection:99` / `assignInspection:141`）都**注册为动作类型**，由 `ConfirmGateway` 两段式入队。
- **不新增任何直接写库路由**。四块能力对 DB 的写入全部经由 action 队列。

### 2.4 水印：端侧 Canvas 合成，原图本地保留

- 水印（门店 + 时间 + 点位 + 责任人）在 Android 端用 Canvas 合成（`media/WatermarkCamera.kt`），原图存 `photos/raw`、成品存 `photos/wm`（`res/xml/file_paths.xml`），通过 `FileProvider`（`AndroidManifest.xml:49-57`）授权相机写入。
- 不依赖服务端处理图片，**追溯不依赖任何服务端图片**。

### 2.5 未配置时降级而非中断

- 对象存储未配置（缺环境变量）时，`/api/qc/media/status` 返回 `configured:false`。
- 此时品控流程**照常完成** AI 识别与结论落库，只是 `photo_url` 为空；admin-web 据此显示**「品控图片暂不可用 + 缺失变量清单」**降级提示，而非报错。

---

## 3. 为什么不是别的方案

| 备选方案 | 否决理由 |
|---|---|
| 照片 base64 存 DB / 落 BFF 盘 | 直接撞红线①，`ci/redline_guard.sh` 会拦，且快照体积爆炸 |
| 引入 AWS SDK / OSS SDK 做预签名 | 违反「BFF 零依赖」，增加供应链与密钥面 |
| 品控照片也走端侧本地（与巡检一致） | 违背 A 块需求：后台必须能看不合格大图 |
| 巡检照片也上对象存储 | 成本 + 隐私，且用户已明确「只存本地」 |
| 为品控新增一个 `/api/qc/commit` 登记态 | 多一套中间态与不一致可能，不如随动作提交（2.1） |
| 未配置时直接报错让品控不可用 | 现场不能因为「后台没配存储」就停下出餐 |

---

## 4. 保了什么

- **红线①（图片不落盘）**：两条路径都不让字节进 BFF；`qc_media` 主动拒收 base64，`inspection` 丢弃并标记。
- **红线②（写回唯一入口）**：四块能力的全部写操作都是注册动作，经队列落地。
- **零依赖**：预签名自研 SigV4，无第三方 SDK。
- **降级不崩**：媒体未配置时品控主流程不中断，前端明确标注。
- **留痕与负责到人**：强制放行必填原因（`insertQcForcePass`，`ops.js:274`）；品控扩展了 `stage`/`operator`/`station` 等责任字段（迁移 003）。

## 7. 副作用与遗留

- **降级可见**：对象存储未配置时，后台看不到品控原图（仅识别与结论可用）——这是刻意取舍，已在 UI 明示。
- **SOP 视频侧缺测试**：`/api/kitchen/sop-videos` 目前无算法/路由测试覆盖（四块能力中唯一缺口），仅校验 URL 不校验可达性。
- **巡检「已拍照」的可信边界**：`done` 由端侧上报的 `photo_taken` 标志决定，服务端无法验证照片内容（因照片不上云）；属「信任终端」的既知边界。
- **强制放行无二次审批**：`qc.force_pass` 一人即可放行（业务确认允许），仅要求必填原因留痕。
- **预签名过期**：读取 URL 有过期时间，后台需在过期后重新 `sign`（`QcPage` 每次加载都会刷新）。

## 8. 回档方案

本 ADR 对应的代码集中在**新增文件**，回档只需：

1. 从 `bff/server.js` 的 `ROUTES` 移除 `qc_media`/`sop_media`（`:75,:76`），保留 `modules`（巡检端点随文件移除而失效）；
2. 删除 `bff/routes/qc_media.js`、`bff/routes/sop_media.js`、`bff/lib/objstore.js`、`bff/lib/algorithms/inspection*.js`、`bff/lib/inspection*.js`；
3. 迁移 003/004 为**加列/建表**，回档时保留列与表即可（不删除，避免历史数据丢失），仅停用端点；
4. Android/admin-web 侧删除对应页面与 `AppModule` 装配行（`qcMediaRepository`/`inspectionRepository`）。

不涉及对既有表结构的破坏性变更，回档风险低。
