## 1. 经营分析 analysis

### 目标与角色
- **目标**：把分散在销售收银/库存/补货的数据翻译成"老板一眼看懂店"的趋势、热力、矩阵与关联结论，支持时段切换与单品钻取。
- **角色**：老板（主看）/ 店长（运营复盘）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 趋势 an-trend | 营收/毛利 4 周折线、各色周表现、AI 下周建议 |
| 时段 an-heat | 24h×7 天热力图、午 11:30 / 晚 18:30 双峰标注、天气关联 |
| 菜单矩阵 an-mx | 波士顿四象限（明星/问题/金牛/瘦狗），9 款饺子 + 招牌菜定位 |
| 效率 an-eff | 翻台率/坪效/人效三仪表盘、同环比、天气节假日关联 |

### 关键交互细节（状态流转/边界/异常）
- **时段切换状态机**：`今日 → 昨日 → 本周 → 上周 → 本月` 五态单选；切换后并行触发"营收/毛利折线 + 各色表现 + 同环比"三组只读查询，加载中文案 `数据生成中…`，失败回退上次成功快照并红字标 `数据异常`。
- **矩阵点击钻取**：四象限气泡（半径=销量、色=菜品色）可点击 → 钻取该 SKU 详情卡（销量/毛利/成本拆解/原料价波动/近 4 周趋势），返回保留筛选态。
- **阈值/边界**：热力图色阶 `0 → 峰值` 四档（#EEF1F5 / #FBD3CC / #F48FB1 / #C2185B）；矩阵分象限基线 = 9 款饺子销量中位数与毛利中位数；天气关联需 ≥ 4 周样本才出结论，不足显 `样本不足`。
- **异常**：单品钻取若该 SKU 无成本拆解（`dishRecipeCost` 未跑），显 `成本待测算`，不阻断销量展示。

### 数据来源与写回
- 来源：店内 SQLite（`sales` / `orders` / `dishes` / `ings`）+ 云端只读副本；天气/节假日来自外部 API。
- **只读输出层**：本模块全只读聚合，零写回；不调 `dishRecipeCost` 改库，仅只读取数。
- 关联：成本结论复用 v1.0 `dishRecipeCost()`（只读调，不改）。

### 与 AI/Kimi 的结合点
- AI 下周建议（5 条）：红色主推前置 / 黑色试点 +¥0.5 / 绿色探新馅料 / 洼地设五福套餐 / 周六晚峰加排 1 人。
- 天气关联结论由 LLM 取确定性函数结果生成，不自行算账。

### 验收标准
1. 时段切换 ≤ 1s 内完成三组图表刷新，UI 明示更新时间。
2. 矩阵气泡点击可钻取单品详情，返回保留筛选。
3. 天气关联结论标注样本周数；样本 < 4 周时不出结论。
4. 全模块零写库动作。

### 建议落地期
P0

## 2. 排班员工 staff

### 目标与角色
- **目标**：把"人"的时间、出勤、绩效、培训、合规串成一张周表，临期自动提醒。
- **角色**：店长（排班/审批）/ 老板（看绩效/合规）/ 员工（打卡/跟做）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 排班 st-sched | 周排班表（A 早 9–17 / B 中 11–21 / C 晚 14–23 / 休 / 请假）、工时汇总 |
| 打卡 st-clock | 应到/实到、在岗/迟到/缺勤计数、打卡明细 |
| 绩效 st-perf | 排行榜（出品/废品/服务/实收）、工时 vs 产出 |
| 培训 st-train | SOP 进度（n/5）、健康证到期预警、着装 Kimi 拍照 |

### 关键交互细节（状态流转/边界/异常）
- **打卡状态机**：`应到 → 已打卡(准点 / 迟到+分钟) / 缺勤`；迟到阈值 = 班次开始 +10 分钟（可配），超 30 分钟记缺勤；当日未打卡且已过班次 1 小时 → 自动转"待说明"推送店长。
- **换班审批流**：`发起换班（A 申请 / B 顶班）→ 待 B 同意 + 店长审批 → 已确认写回排班表 / 已驳回`；任一节点拒绝回退到原排班；写回走 **经确认 → /api/sync（带 rev）**。
- **健康证临期阈值**：`>30 天 绿 / 14–30 黄 / 7–14 橙 / <7 红 / 逾期 禁止上岗`；首页预警中心同步红色项；逾期员工排班表显灰底"禁岗"。
- **培训进度**：`0/5 → n/5 进行中 → 5/5 已通过`；关键工艺点（料水分三次加入 / 分三次点凉水 / 醒发 30 分钟）AI 抽查提问，未通过不得上岗对应 SKU。
- **异常**：换班冲突（B 已排班）拦截并提示替代人选。

### 数据来源与写回
- 来源：排班/打卡/绩效/培训进 SQLite 新增表（`staff_shifts` / `staff_clock` / `staff_perf` / `staff_train`），与既有员工档案关联。
- 写回：换班确认、打卡补录、培训通过 → **经确认 → /api/sync（带 rev）**；绩效排行只读聚合。
- 健康证/证照档案：来自 foodsafe 模块联动，本模块只读引用。

### 与 AI/Kimi 的结合点
- 着装/SOP 合规拍照（Kimi `uniform`）：识别工服/帽子/口罩/洗手/SOP 合规，置信度 ≥ 90% 入合规档，< 90% 标"待复核"。
- 周六晚峰加排建议来自 analysis 模块天气关联。

### 验收标准
1. 迟到阈值可配，默认 +10 分钟；超 30 分钟自动记缺勤。
2. 健康证 < 7 天红色，逾期员工排班表显禁岗。
3. 换班需 B + 店长双确认，写回带 rev。
4. 培训未通过对应 SKU 工单不让该员工接单。

### 建议落地期
P0

## 3. 会员营销 vip

### 目标与角色
- **目标**：把会员资产（储值/积分/券）与营销动作（生日券/活动券/社群）串成可衡量 ROI 的闭环。
- **角色**：老板（看资产/拍板发券）/ 店长（执行发券/核销）/ 收银（扣储值/核销券）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 概览 vip-overview | 会员资产总额、结构（储值/积分/普通）、近 4 周新增 |
| 储值 vip-balance | 充值/消费/净增周条、大额储值明细 |
| 优惠券 vip-coupon | 已发/已核销/待发/过期未用、活动券效果星级 |
| 生日 vip-birthday | 本周生日会员、企微社群活跃 |

### 关键交互细节（状态流转/边界/异常）
- **储值消费扣减状态机**：`余额 ≥ 消费额 → 扣减 → 写回(经确认 → /api/sync) → 余额更新`；`余额 < 消费额 → 拒绝扣减 + 提示充值`；储值扣减与现金/扫码支付可混合，扣减项单独走确认队列。
- **券核销状态机**：`待发 → 已发 → 已核销 / 过期未用`；过期阈值 = 发券日 + 有效期（默认 30 天），过期券自动归档不可核销；核销需扫码或输券码 + 收银确认。
- **生日券自动触发 ≠ 自动发送**：生日前 7 天 AI 生成发券建议（储值会员赠长寿红饺 + 8 折券；普通会员赠 8 折券）→ 待老板/店长确认 → 发券（**经确认 → /api/sync**）；未确认前仅停留在"建议"态，不触达会员。
- **大额储值风控**：单次充值 ≥ ¥1,000 自动标黄复核（防套现/洗钱），需店长二次确认才到账。
- **异常**：券码重复核销拦截（状态机 + rev 锁），二次核销显 `券已核销`。

### 数据来源与写回
- 来源：会员/储值/积分/券进 SQLite 新增表（`vip_members` / `vip_balance` / `vip_coupons` / `vip_recharge`）；企微社群数据来自企微 API。
- 写回：储值扣减、券核销、生日券发送 → **经确认 → /api/sync（带 rev）**；资产总额、结构、新增趋势只读聚合。
- 不直接对接支付通道：储值充值走既有收银，本模块只记余额变化。

### 与 AI/Kimi 的结合点
- 生日券建议由 AI 生成（储值/普通差异化），需确认才发。
- 活动券效果星级由 AI 评（核销率/客单提升/复购）。

### 验收标准
1. 储值余额不足时拒扣并提示充值，不出现负余额。
2. 券核销带状态机 + rev 锁，重复核销被拦截。
3. 生日券仅"建议"态，未确认不触达会员。
4. 单次充值 ≥ ¥1,000 触发店长复核。

### 建议落地期
P1

## 4. 堂食收银 pos

### 目标与角色
- **目标**：把桌台、点餐、收银、实收串成实时看板，老板离店也知"几张桌在用、今天收了多少"。
- **角色**：收银/店长（操作）/ 老板（看实收/翻台）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 桌台 pos-floor | 12 桌平面图四态（空闲/用餐/待清/预订）、占用统计 |
| 收银 pos-pay | 支付方式占比（微信/支付宝/现金/储值）、支付明细 |
| 实收 pos-real | 今日实收总额、小时柱、翻台/桌均/人均仪表盘 |

### 关键交互细节（状态流转/边界/异常）
- **桌台状态流转**：`空闲 → 预订(锁定时段) / 开台(用餐) → 待清(买单后) → 清台 → 空闲`；预订桌在预订时段前 15 分钟自动从空闲转预订，超时未到由 booking 模块释放回空闲。
- **并单/拆单**：并单 = 多桌合到一单（需同桌台组）→ 写回 **经确认 → /api/sync**；拆单 = 一桌拆多单（按人头/菜品）→ 同上；并/拆单均生成新单号，原单作废留痕。
- **多支付混合结算**：单笔可组 `微信 + 支付宝 + 现金 + 会员储值`，各成分 ≥ 0 且合计 = 应收；储值成分走 vip 模块扣减确认；现金成分记应收。
- **挂账**：`应收 → 挂账(记债权人/到期) → 后续结算(冲销)`；挂账进应收表，不直接进实收，结算单只读输出层展示。
- **边界**：结算单（进货/对账下游）**只读输出层不写 DB**，本模块只展示；实收聚合只读。
- **异常**：并单桌台组不一致拦截；拆单后任一子单未结前不可清台。

### 数据来源与写回
- 来源：桌台/订单/支付进 SQLite 新增表（`pos_tables` / `pos_orders` / `pos_payments` / `pos_hanging`）；实收聚合自 `pos_payments`。
- 写回：桌台状态变更、并/拆单、混合支付、挂账 → **经确认 → /api/sync（带 rev）**；实收总额、支付占比只读聚合。
- 结算单：只读输出层，数据来自 `DB.recv`，模板存独立 localStorage，**不写 DB**（同 v1.0 红线）。

### 与 AI/Kimi 的结合点
- 晚峰翻台预估来自 booking 模块；实收异常涨跌由 AI 推送（analysis 联动）。
- 暂无 Kimi 拍照用例（点餐扫码走 C 端小程序，非本产品边界）。

### 验收标准
1. 桌台四态流转可逆性正确，预订超时由 booking 释放。
2. 混合支付各成分 ≥ 0 且合计 = 应收，储值成分走确认队列。
3. 并/拆单带 rev，原单作废留痕。
4. 结算单不写 DB，实收聚合只读。

### 建议落地期
P0

## 5. 外卖平台 takeout

### 目标与角色
- **目标**：聚合美团/饿了么/抖音三平台单量营收评分，T+1 对账，差评闭环。
- **角色**：店长（对账/差评回复）/ 老板（看占比/评分趋势）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 概览 to-overview | 外卖营收/单量/占比、平台分布、外卖热销 TOP |
| 对账 to-reconcile | T+1 待结算、对账明细、平台扣点 |
| 差评 to-bad | 差评预警、原因分析、回复审批 |

### 关键交互细节（状态流转/边界/异常）
- **差评预警阈值**：`评分 ≤ 3 星` 或 `命中关键词（慢/咸/冷/少/破）` → 红色预警推送老板 + 店长；预警关联订单号与平台，自动跳转差评回复。
- **差评回复审批流**：`输入回复 → 待店长审批 → 已通过(发送至平台 API) / 退回(改写)`；快捷模板（致歉+红包 / 邀复购 / 升级投诉）可选；回复发送走平台 OpenAPI，**不写本地 DB**，仅记回复日志。
- **对账差异处置状态机**：`T+1 拉取平台账单 → 与本地销售核对 → 一致(自动入账标记) / 差异(金额或单号不符) → 差异挂起人工核对 → 已处理(补单/冲销/挂账)`；差异项标黄，超 24 小时未处理标红推送。
- **平台扣点边界**：扣点率按平台配置（美团 18% / 饿了么 16% / 抖音 T+7 到账），实收 = 营收 × (1 - 扣点)。
- **异常**：平台 API 失败重试 3 次后降级为"上次成功快照"，UI 标 `平台数据滞后`。

### 数据来源与写回
- 来源：三平台 OpenAPI（订单/评分/账单）→ SQLite 新增表（`takeout_orders` / `takeout_reviews` / `takeout_reconcile`）。
- 写回：差评回复发送走平台 API（不写本地 DB，仅记日志）；对账差异处置（补单/冲销）→ **经确认 → /api/sync（带 rev）**。
- 外卖对账为**只读核对层**，结算单不写 DB（同 v1.0 红线）。

### 与 AI/Kimi 的结合点
- 差评原因分析由 AI 生成（关键词 + 订单关联 + 时段并发），附改进建议。
- 回复模板由 AI 起草，店长审批。

### 验收标准
1. 评分 ≤ 3 星或命中关键词必触发红色预警。
2. 回复必经店长审批，发送走平台 API 不写本地 DB。
3. 对账差异超 24 小时未处理标红推送。
4. 平台 API 失败重试 3 次降级快照并明示。

### 建议落地期
P1

## 6. 预订排队 booking

### 目标与角色
- **目标**：把预订、排队、翻台预估串成实时看板，老板离店知道"今天几桌预订、排队到几号"。
- **角色**：店长/迎宾（操作）/ 老板（看预览）。

### 关键功能
| 子页 | 功能 |
|---|---|
| 今日预订 bk-today | 预订清单（时段/人数/桌号/电话/状态） |
| 排队叫号 bk-queue | 当前叫号、等位数、等位时长、候餐服务 |
| 翻台预估 bk-turn | 平均翻台时长、时段占用预估 |

### 关键交互细节（状态流转/边界/异常）
- **预订状态机**：`待确认 → 已确认 → 已到店(入座) / 超时未到释放 / 取消`；待确认需店长/迎宾电话回访后确认；已确认在预订时段前 15 分钟锁定桌台（联动 pos 桌台流转）。
- **超时未到释放**：`预订时间 + 15 分钟（可配）未到 → 自动释放桌台 → 转排队可用`；释放前 5 分钟推送提醒顾客，释放后推送店长。
- **排队叫号顺序**：`取号 → 等位 → 叫号中 → 就座中 → 已入座 / 流失(等位超阈值离店)`；FIFO 顺序，大桌/小桌分队列；叫号后 10 分钟未入座自动回退到队首 +1。
- **翻台预估**：按桌型（大桌 ~12 分 / 中桌 ~8 分 / 包间 ~15 分）+ 当前用餐进度估算；晚峰占用率 ≥ 90% 时推送"建议加排 1 人服务"。
- **异常**：重复取号拦截（手机号去重）；预订桌台已被占用时提示替代桌。

### 数据来源与写回
- 来源：预订/排队进 SQLite 新增表（`bookings` / `queue`）；翻台预估读 `pos_tables` 状态。
- 写回：预订状态变更、排队叫号、桌台释放 → **经确认 → /api/sync（带 rev）**；翻台预估、占用率只读聚合。
- 与 pos 模块联动：预订桌台状态双向同步。

### 与 AI/Kimi 的结合点
- 晚峰占用率 ≥ 90% AI 推送加排建议（联动 analysis/staff）。
- 等位流失预警：等位超 30 分钟未入座标黄，超 45 分钟标红。

### 验收标准
1. 预订状态机四态完整，超时 15 分钟自动释放桌台。
2. 释放前 5 分钟推送顾客，释放后推送店长。
3. 排队 FIFO，叫号 10 分钟未入座回退队首。
4. 占用率 ≥ 90% 推送加排建议。

### 建议落地期
P0

## 8. 设备能耗 equipment

## 9. 财务税务 finance

### 目标与角色
- **目标**：把发票、税务预估、现金流、股东分账串成财务看板，发票额度可控、分账有冻结期。

### 关键交互细节（状态流转/边界/异常）

- **结算单审批**：结算单（供应商/薪资）**只读输出层不写 DB**，审批后由人工入账（同 v1.0 红线）。
- **异常**：开票金额超剩余额度拦截；分账冻结期内尝试提现拦截。

### 数据来源与写回
- 来源：发票/税务/现金流/分账进 SQLite 新增表（`fin_invoices` / `fin_tax` / `fin_cash` / `fin_split`）；现金流聚合自既有表。

### 验收标准
1. 开票必经老板审批，额度不足拦截。

3. 分账冻结期 7 天，冻结期内提现拦截。

### 关键交互细节（状态流转/边界/异常）
- **报损单审批流**：`录入(附照片/原因/数量/金额) → 待店长审批 → 已审批(写回库存) / 退回(补材料)`；报损单必附照片或原因，否则拦截；审批后扣减库存（走 rev 三向合并，核心零改动）。
- **损耗阈值预警**：`月损耗率 > 1% 黄 / > 1.5% 红`；红色推送老板 + 店长；按原料看占比，单原料损耗 > 30% 总损耗标"重点关注"。
- **盘亏盘盈写回**：`盘点差异(盘亏-/盘盈+) → 待确认 → 写回(经确认 → /api/sync)`；盘亏扣库存、盘盈加库存，均走 rev 三向合并；盘盈需附原因（入库多送/分份误差）。
- **损耗原因分类**：`过期 48% / 制作损耗 28% / 运输破损 24%`（占比可配）；原因分类影响改进措施（过期→补货量调减，制作→分份规范，运输→包装改进）。
- **异常**：报损金额 > ¥500 需老板二次确认；盘点差异 > 5% 库存量拦截并要求复盘。

### 数据来源与写回
- 来源：报损/盘点进 SQLite 新增表（`loss_reports` / `loss_inventory_diff`）；损耗分析聚合自 `loss_reports`。
- 写回：报损单审批、盘亏盘盈 → **经确认 → /api/sync（带 rev）**；损耗分析、原因占比只读聚合。
- 库存重放走 v1.0 `rebuildStock()`（受保护），本模块只调 rev 合并，不改核心。

### 与 AI/Kimi 的结合点
- 损耗原因占比由 AI 归因，联动改进措施（过期→补货量调减联动 inventory 补货建议）。
- 盘点差异可联动 Kimi `stock` 拍照盘点（v1.0 进销存内）。

### 验收标准
1. 报损单必附照片/原因，否则拦截。
2. 损耗率 > 1% 黄、> 1.5% 红推送。
3. 盘亏盘盈写回带 rev 三向合并，核心零改动。
4. 报损金额 > ¥500 老板二次确认。
5. 盘点差异 > 5% 拦截要求复盘。

### 建议落地期
P2

## 14. Kimi 视觉模块（总览）

### 目标与角色
- **目标**：用拍照 + 视觉识别替代人工录入与核对，覆盖验货/盘点/品控/摆盘/留样/着装 6 处用例，统一交互、统一红线。
- **角色**：库管（验货/盘点）/ 厨师长（品控/摆盘）/ 店长（留样/着装）/ 老板（看识别结果）。

### 6 处用例一览
| 用例 | key | 所在模块 | 识别内容 | 置信度样例 | 处置 CTA |
|---|---|---|---|---|---|
| 验货 | recv | 进销存·进货 | 数量/鲜度/规格/批次/检验报告 | 98% | 登记入库 |
| 盘点 | stock | 进销存·库存 | 估算库存并核对账面 | 96% | 生成补货单 |
| 品控成品 | qc | 厨房·品控 | 褶纹/色泽/形态/重量估值 | 95% | 复核通过 |
| 摆盘质检 | plate | 厨房·品控 | 摆盘规范/分量/配色/点缀 | 93% | 复核通过 |
| 留样登记 | sample | 食安·留样 | 菜品/克重/标签/48h 到期 | 91% | 登记留样 |
| 着装合规 | uniform | 排班·培训 | 工服/帽子/口罩/洗手/SOP | 90% | 记录合规 |

### 统一交互（拍照→扫描动效→识别卡片→处置按钮）
1. **拍照入口**：`photo-cap` 卡片，文案"对准 XX · Kimi 识别 YY"。
2. **扫描动效**：点击 → `scanning` 类 900ms 扫描动画 → 调 `/api/kimi/vision`。
3. **识别卡片**：紫色 `kimi-card`，头部标题 + 置信度，中部多行识别项（pass/warn/fail 三态圆点），底部原图/识别框/对比三缩略图 + 建议备注 + CTA 按钮。
4. **处置按钮**：CTA 点击 → 触发对应写动作（经确认 → /api/sync）或只读记录。

### 红线（只识别 + 建议，写操作需确认）
- **Kimi 仅识别 + 建议**，不直接写库；所有 CTA 走确认台（`openSheet('confirm')`）→ 云端队列 → 店内消费器 → /api/sync（带 rev）。
- 置信度阈值：`≥ 90% 入档 / < 90% 标"待复核"`；验货/留样等强合规用例阈值更高（≥ 91%）。
- 色源锁定不可由 Kimi 改：红色必须火龙果，识别到非火龙果色源标"色源异常"警告，不改配方。
- 不替代计价/库存重放：识别结果仅作录入辅助，落库仍走 rev 三向合并。

### 与 `/api/kimi/vision` BFF 的关系
- **契约位置**：详细契约另见《Kimi 视觉 API 调用契约》（独立文档），本节仅述关系。
- **调用链路**：`App/管理后台 拍照 → 上传图 → BFF /api/kimi/vision {type, image} → 调 Kimi 视觉模型 → 返回 {title, rows[], note, cta, conf} → 端侧渲染 kimi-card`。
- **入参**：`type`（recv/stock/qc/plate/sample/uniform）+ `image`（base64 或 OSS URL）+ 上下文（批次号/SKU/员工 ID）。
- **出参**：`title` + `rows[[item, value, status]]` + `note`（建议）+ `cta`（处置动作文案）+ `conf`（置信度）。
- **成本控制**：按用户限流 + 缓存同类识别（同批次验货 1 小时内复用）；失败重试 2 次降级为"识别失败，请人工录入"。
- **写回分流**：CTA 触发的写动作按用例分流到对应模块确认台（recv→inventory 入库 / stock→inventory 补货 / qc/plate→kitchen 品控记录 / sample→foodsafe 留样 / uniform→staff 合规档）。

### 验收标准
1. 6 处用例拍照→扫描动效→识别卡片→CTA 流程统一。
2. 置信度 < 90% 标"待复核"，强合规用例 < 91% 待复核。
3. 所有 CTA 走确认台，不直接写库。
4. 色源异常标警告，不改配方。
5. /api/kimi/vision 失败重试 2 次降级人工录入。

### 建议落地期
P1（验货/盘点/留样 P0 可先行，品控/摆盘/着装 P1）
