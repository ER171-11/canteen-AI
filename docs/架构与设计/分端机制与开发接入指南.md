# 分端机制与开发接入指南

> 面向 agent / 开发者的操作手册：读懂系统的"分端 + 角色权限 + 跨端写回"机制，并知道新增/修改功能时该改哪些文件。
> 代码基线：main 分支。相关设计文档：`docs/熊猫五福餐厅_PRD_v1.0.md`、`docs/decisions/ADR-*`、`HANDOFF.md`。

---

## 1. 一句话机制

系统**没有**为老板/店长/厨师各写一套后端，也**没有** feature-flag 模块开关。分端 = **一套 BFF + 一套 RBAC 权限模型 + 三套前端壳（admin-web / Android / iOS）**。

- 角色可见模块由 **岗位权限码（permissions）** 决定，不因"端"而变。
- 同一老板账号在 Android 与 admin-web 看到的模块集**收敛一致**，差异只在 UI 形态。

```
bff/data/org.json（岗位 permissions）
        │  登录签发
        ▼
token{ role, permissions[], store_id, can_write }
        │
        ├─ admin-web : rbac/roles.ts（静态路径谓词）+ config/menu.tsx → 菜单过滤 + 403 守卫
        ├─ Android   : AppModule.can(module)/canOpenRoute → Tab/模块目录过滤
        └─ iOS       : 同一 permissions 模型（当前多为骨架）
        │
   BFF server.js：统一鉴权（401）
   BFF actions.js：写动作角色闸门（403）→ 队列 → confirm → consumer → /api/sync
```

## 2. 角色与权限模型（权威定义在 BFF）

### 2.1 模块常量（16 个）—— `bff/lib/org.js:16-20`

```
inventory, kitchen, pos, booking, foodsafe, staff, finance, vip,
takeout, analysis, supply, loss, equipment, review, actions, org
```

权限码格式：`{module}.{read|write}`（如 `inventory.read`、`actions.write`）。

### 2.2 岗位种子（6 个）—— `bff/lib/org.js:50-99`（`defaultOrg().positions`）

| 岗位 id | name | 权限特征 |
|---|---|---|
| `pos_boss` | 老板 | 全部 `read+write` |
| `pos_manager` | 店长 | 全部 rw，**去掉 `org.write`** |
| `pos_cashier` | 收银 | pos/booking/vip/takeout/actions rw + inventory/kitchen/analysis read |
| `pos_kitchen` | 厨房 | kitchen/foodsafe rw + inventory/actions/analysis read |
| `pos_finance` | 财务 | finance/analysis rw + supply/actions/inventory/vip/takeout read |
| `pos_readonly` | 只读 | 全部 `read` |

> 注意：业务口的"厨师长 / 采购 / 库管"**不是独立枚举**，落在 `pos_kitchen` 与 `inventory`/`supply` 权限上。

### 2.3 登录与 token —— `bff/lib/auth.js`

- `issueToken()`（`:31-65`）：token 内嵌 `role / permissions / store_id / can_write`。
- `ROLE_MAP`（`:12`）：demo 账号→角色映射；`WRITE_ROLES`（`:13`）粗粒度可写角色。
- `mayWriteActions()` / `hasPerm()`（`:133-148`）：写动作与权限校验函数。

### 2.4 前端角色枚举 —— `apps/admin-web/src/api/types.ts:8`

```ts
export type Role = '老板' | '店长' | '财务' | '厨房' | '收银' | '只读'
```

## 3. 各端如何"只看到自己的模块"

### 3.1 admin-web（静态谓词表 + 双保险）

- **角色→路径谓词表** `apps/admin-web/src/rbac/roles.ts:7-31`（`RULES`），`老板: () => true`，其余按路径前缀过滤。
- **`canAccess(role, path)`**（`:33-37`）、**`firstAccessiblePath(role)`**（`:40-48`，登录落地页）。
- **菜单过滤** `apps/admin-web/src/layouts/MainLayout.tsx:73-90`：`MENU` 逐叶 `canAccess` 过滤，空分组丢弃。
- **路由 403 兜底** `MainLayout.tsx:92-94, 202-218`：手输 URL/深链也拦截。
- **菜单定义** `apps/admin-web/src/config/menu.tsx`（9 组，叶子 `path/title/reserved`）。
- **路由注册** `apps/admin-web/src/App.tsx`（import + `<Route path=... element=.../>`）。

> admin-web 的角色→模块映射是**前端静态常量**（`roles.ts` 的 `RULES` + `menu.tsx` 的 `MENU`），**不读 token 的 permissions 明细、不云端下发**。

### 3.2 Android（动态读 token 的 permissions）

- 权限判断 `apps/android-app/.../AppModule.kt`：
  - `can(module, write)`（`:197-203`）：老板/店长全开；其它看 `{module}.read|write`。
  - `moduleOfRoute(route)`（`:206-218`）：路由→模块名映射。
  - `canOpenRoute(route)`（`:238-241`）：门禁。
- 路由表 `apps/android-app/.../ui/AppNav.kt:73-138`（`Routes` 对象）。
- 模块目录单一事实源 `apps/android-app/.../ui/BossIa.kt`（`BossIa.modules` / `goodsEntries` / `Mine.*`）。
- 会话持久化 `apps/android-app/.../auth/SessionStore.kt`（token/role/permissions 落盘，支持离线）。

### 3.3 BFF（统一鉴权 + 写闸门，读不按角色过滤）

- 入口鉴权 `bff/server.js:184-219`：Bearer 校验，白名单外 `/api/*` 无 token → 401。
- **关键边界**：绝大多数**只读**端点只要求"有效 token"，**不做按角色的模块过滤**——读权限过滤实际发生在前端（菜单/路由）。
- **写接口才做角色闸门**：`POST /api/actions` 需 `actions.write`，否则 403（`bff/routes/actions.js:258-266`）；组织写需 `org.write`。

## 4. 跨端任务流（唯一写枢纽 = `/api/actions`）

所有写操作（无论哪端哪角色）都不直写店内库，统一进写回队列。

### 4.1 状态机 —— `bff/routes/actions.js:1-19`

```
queued（入队）→ confirm（校验 rev + 可写角色）→ 待执行
             → execute（消费者回调 / BFF apply）→ 已执行 / 已驳回
             → 24h 未执行 → 已过期
```

### 4.2 分级授权 —— `bff/lib/policy.js`

- L0 只读 / L1 草稿（默认永不自动）/ L2 政策内自动（可审计+可回滚）/ L3 必人工确认。
- `NEVER_AUTO`（`:19-23`）：高风险 type 永不允许自动执行（`dish.price`、`recipe.upsert`、`finance.approve`、`pos.pay` 等）。

### 4.3 典型跨端协作流：补货/采购 → 审批 → 入库

```
Android（厨房/采购岗）勾选补货意向 → POST /api/actions（restock.create，queued）
        ↓
admin-web 审批中心 或 Android 审批队列 → confirm（店长/老板，校验 rev）→ 待执行
        ↓
店内 consumer 拉取 → /api/sync（rev 乐观锁）落库 → execute 置"已执行"
        ↓
下一轮快照回写 → 各端看到"已执行"（幂等：5 分钟窗口防连点重复入库）
```

## 5. 开发接入决策树

| 类型 | 典型诉求 | 是否动机制 |
|---|---|---|
| A. 改现有页面展示 | 改文案/加列/调样式 | ❌ 几乎不用 |
| B. 新增**只读**模块/页面 | 加"看数据"的页 | 需接权限过滤 |
| C. 新增**写操作** | 加"改数据"的能力 | 必须走 actions 队列 |
| D. 新增**角色/岗位** | 加"采购主管"岗位 | 三处注册 |
| E. 调整某角色**能看什么** | 店长不再看财务 | 改权限码（双轨） |

## 6. 各类操作 step-by-step

### A. 改现有页面
直接改 `apps/admin-web/src/pages/**` 对应页面；角色可见性不变。

### B. 新增只读模块/页面
1. **BFF 只读端点**（参考 `bff/routes/export.js`，红线"只读不写"）：`loadSnapshot()` 读快照 + 纯计算 + 返回 JSON/CSV；注册到路由分发。
2. **admin-web 页面** `apps/admin-web/src/pages/xxx/XxxPage.tsx`。
3. **注册路由** `apps/admin-web/src/App.tsx`（import + `<Route>`）。
4. **加菜单** `apps/admin-web/src/config/menu.tsx` 对应分组 `children`。
5. **给非老板角色加可见谓词** `apps/admin-web/src/rbac/roles.ts` 的 `RULES`（**漏了只有老板能看**）。
6. （可选）Android：`AppNav.kt` 的 `Routes` + composable；`AppModule.moduleOfRoute` 映射；`BossIa.kt` 模块目录。

### C. 新增写操作
前端**禁止直写库**，统一 `POST /api/actions {type, payload, operator}`，再 `POST /api/actions/{id}/confirm`。

- 入队不校验 type 白名单；执行时 `executeAction` 查算法登记表（`bff/lib/algorithms/execute.js:92-96`），未登记 → `need-manual` 交店内 consumer。
- **落点二选一**：
  - BFF 算法层（快照内能算完）：在 `bff/lib/algorithms/registry.js` 用 `registerAll({ 'xxx.type': (ctx,data,payload)=>... })` 登记。
  - 店内 consumer（需真 SQLite 落库）：不登记，走 need-manual。
- **自检四件事**：① `actions.write` 鉴权；② `policy.js` `NEVER_AUTO`（高风险需人工）；③ 幂等（`type+payload+operator` 5 分钟去重，天然生效）；④ 状态机四态展示。

### D. 新增角色/岗位
1. `bff/lib/org.js` `defaultOrg().positions` 加一项（定义 permissions）。
2. `apps/admin-web/src/rbac/roles.ts` `RULES` 加谓词。
3. `apps/admin-web/src/api/types.ts` `Role` 联合类型加字面量。
4. （可选）`bff/lib/auth.js` `ROLE_MAP` 加 demo 映射。

### E. 调整某角色可见模块（双轨，最易踩坑）
| 端 | 权限判断 | 要改 |
|---|---|---|
| admin-web | 静态 `RULES` | `rbac/roles.ts` |
| Android | 动态读 token permissions | 改岗位权限即生效 |

- **临时调权限**：老板在 admin-web「门店岗位账号」改（走 `org.updatePosition`，改 `bff/data/org.json`），Android 自动生效，admin-web 需同步改 `roles.ts`。
- **永久调权限**：改 `org.js` 种子 + 同步 `roles.ts`。

## 8. 踩坑清单

1. **admin-web 与 Android 权限判断机制不同**（静态 `roles.ts` vs 动态 permissions），改权限必须双写，否则两端不一致。
2. **`defaultOrg()` 只是种子**：只改代码种子不影响已初始化的 `bff/data/org.json`；已部署环境要改运行时数据（走 UI 或直接改 org.json）。
3. **只读端点不做角色过滤**：角色可见性完全由前端菜单/路由控制，忘改 `roles.ts` 会导致"只有老板能看"。
4. **写操作必须走 `/api/actions`**，禁止前端直写库；未登记算法的 type 会被判 `need-manual` 而非静默丢弃。
5. **高风险 type 在 `policy.js` 的 `NEVER_AUTO`**，新增写操作需自查是否应加入人工确认名单。
6. **不要提交运行态数据**：`bff/data/`、`bff/.env`、`*.db`、`local.properties` 在 `.gitignore` 内（见 `HANDOFF.md` §5）。
