## 0. 一句话结论

11 张卡**没有一张已被完整实现而应作废**，但有 6 张存在冲突或前置缺失。本 ADR 把这 6 处全部拍板成可执行口径：**回滚走新下推端点、报价导入给 upsert 加 append 模式、手工校准走独立弹窗并复用「手工调整」流水口径、W4 三项统一收口到审批队列并强制前置备份**；同时明确测试期双人确认对老板/店长豁免、只约束员工。

## 3. 决策

### D1 快照回滚（W2-01 / FP-SET-10）—— 新下推端点

- 回滚**不在备份模块内做**（`snapshot_store.js` 只提供 save/list/read）。
- 新增动作 `snapshot.rollback`，payload：`{backup_id, target_rev, reason}`。**不内联整库**。
- 新增**执行器专用**服务端下推端点（建议 `POST /api/snapshot/apply`）：
  - 数据由服务端从 `data/snapshots/<id>.json` 读取后下发；
  - **禁止前端直调**（内部鉴权 / 仅执行器可用），否则即成为绕过 `/api/actions` 的第二条写通道（红线 #1）；
  - 顺带绕开现有 5 MB body 限制。
- 执行链：`提交 → 确认 → 入队 → 执行器读备份 → 校验 schema → 调下推端点 → StoreAdapter.casWrite → rev = max(当前rev, target_rev) + 1 → 写审计（谁、何时、从 rev X 到 rev Y、backup_id）`。
- 必须基于 `StoreAdapter`（ADR-010 Phase 0 接缝），避免 Phase 2 迁云返工。

### D2 报价导入（W2-04 / FP-PRICE-12）—— upsert 加 append 模式

- `quote.upsert` 新增 `append` 模式：
  - 默认行为**不变**（手工录入仍按 `ing+src` 覆盖，FP-PRICE-04 依赖它）；
  - `append: true` 时按 `ing+src+price(+date)` 去重**追加**，命中完全相同的行则跳过（不覆盖）。
- 保留 `quote.import` **批量动作**，内部复用 append helper；避免逐行 `quote.upsert` 变成 N 条队列 = N 次审批。
- 红线（沿用旧 ADR-003）：导入只允许写 `data.quotes`，**禁止**写 `logs` / `ings.stock` / `ings.avg` / `recv`；`conv ≠ 1` 的原料默认跳过，不在导入里自动推断跨单位价格。

### D3 手工校准（W3-01 / FP-ING-05）—— 独立弹窗 + 复用「手工调整」流水

- **入口形态 A（已选）**：后台独立的「校准」弹窗，与「编辑原料档案」分开。
- 均价**允许单独改**（库存不动、只修均价）。
- **强制填原因**（写入流水 `note`，供损耗/审计追溯）。
- **账务写法必须复用 `stock.count` 的「手工调整」流水口径**，禁止用 `ing.upsert` 改存量 `stock/avg`。
- **顺带修复**：`applyStockCount` 的 `inCost: 0` 改为「传入均价 → 否则取该原料现有均价」，修掉「盘点后均价清 0、库存总值变 0 元」的现存缺陷。
- 约束：`ing.upsert` 继续负责主数据维护（含新建初值），**不再作为存量校准入口**。

### D4 高危三件套（W4-01/02/03 / FP-SET-15/16/17）

#### D4-1 角色与确认（测试期）

| 角色 | 看到入口 | 提交 | 一步确认 |
|---|---|---|---|
| 老板 / 店长 | ✅ | ✅ | ✅（**测试期豁免双人**） |
| 员工（收银/厨房/财务…） | ❌ 直接 403 | ❌ | ❌（提交也只能入队，不能自审） |

- 高危动作（`snapshot.rollback` + W4 三项）**仅老板/店长可执行**，沿用 `snapshot.js:152-155` 的角色门槛。
- 测试期**不做「两个不同账号」校验**；改为 **单人确认 + Popconfirm + 手动输入确认词**（如「确认清空」「确认恢复」「确认回滚」）。
- 代码预留 `requireDualApproval` 开关（**默认 false**）；打开后服务端校验 `confirmed_by !== created_by`。

#### D4-2 rev 语义

覆盖后 `newRev = max(当前rev, 导入rev) + 1`，**绝不回退**（否则乐观锁与客户端缓存判断失效），并在回执记录 `fromRev → toRev`。

#### D4-3 强制前置备份

执行器第一步调用 `snapshot_store.save()`；**备份失败即拒绝执行**（不静默降级，红线 #7）。备份 id 写入动作回执与审计。

#### D4-4 W4-02 基线制品来源

- 现状无可用基线（`data.seed` 是空快照；真实基线在 `store-inventory/data/餐厅系统.db`，不随包）。
- 选 **A：打包 `baseline.json`**——新增生成脚本从遗留库导出一次，产物随包发布，带 `baseline_version` + 校验和。
- 引用 ADR-001 口径：基线 = 海南菜篮子 84 行实收明细建立的原料目录 + 采购单 + 86 道保本菜单；**销售 / 报价 / 配方为空属正常**。
- UI 必须明示「将丢弃 N 条销售 / N 张进货单 / N 条流水」，不能只写「重置」。

#### D4-5 W4-03 清空档位

- 两档：`scope: 'business'`（默认，只清业务）/ `scope: 'all'`（回到首次安装状态）。
- `scope: 'business'`：`ings / dishes / orders / recv / sales / quotes / logs / rec / loss_*`；
- `scope: 'all'`：额外清 `config / rest / org / 词表 / 结算模板 / 点位`（会登出、店名丢失，需二次确认词）。

#### D4-6 清空分组约束（技术硬约束）

`ings / recv / logs` **必须同组清**：
- 只清 `ings` → 流水悬空；
- 只清 `logs` 而保留 `recv` → 下次 `rebuildStock` 会从进货单**把库存又算回来**。

#### D4-7 W4-01 恢复范围

**整包 `data + ext`** 一起恢复（ext 是 60+ 张业务表，只恢复 data 会出现「库存对了、食安/财务/排班全空」的半残状态），并过 `SCHEMA_VERSION` 升版。

**W3-01 手工校准**
- `applyStockCount` 支持 `avg`：payload 增 `avg`；`inCost = avg ?? 该原料现有均价`（修掉清 0）。

- 前端：多选原料 → 批量设置。

### 8.4 不要做的事（已踩过的坑）

1. **不要**用 `POST /api/snapshot/push` 实现「导入恢复」——那是绕开队列的直写。
2. **不要**用 `maint.row_delete` 或 `push` 空 `data` 实现「清空业务数据」。
3. **不要**用 `ing.upsert` 改存量 `stock/avg`——会被 `rebuildStock` 冲回。
4. **不要**把「库存/均价」加进原料档案编辑表单（会和主数据编辑混淆）。
5. **不要**把回滚做成前端可直调的新端点（会形成第二写通道）。
6. **不要**把 `data.seed/snapshot.json` 当「真实数据基线」——它是空快照。
7. **不要**只清 `logs` 或只清 `ings`——`recv` 会把库存重算回来。
8. **不要**改完 `bff/` 忘记跑 `sync-assets.js`——桌面端会用旧代码打包。
9. **不要**在只有 1 份旧备份（rev 291）时直接回滚——先打新备份。
10. **不要**把整库快照内联进动作 payload（W4-01 用暂存区 `data/imports/<id>.json` + `import_id`）——审批中心会被整库撑爆。
11. **不要**改已发布的 `bff/baselines/baseline-v1.json`——新增 `--version=v2` 另存；改旧版会让所有历史回执的校验和对不上。

### 8.7 第 2 批落地说明（2026-10-30）

## 9. 遗留与待观察

- **ADR-010 Phase 2 迁云**：本 ADR 的 `StoreAdapter` 依赖是硬要求，迁云后回滚/导入/清空都应零返工；若届时形态变化，需另立 ADR 修订 §D1/§D4。
- **`requireDualApproval` 开关**：测试期默认关；正式多账号环境启用前需补「提交人 ≠ 确认人」的服务端校验与用例。
- **基线制品版本化**：`bff/baselines/baseline-v<ver>.json` 一旦发布即视为不可变；后续基线变更须 `gen-baseline.js --version=vN` 新增版本号，不改旧版（第 4 批已按此落地 v1）。
- **导入暂存区不自动过期**：`data/imports/` 只按「保留最近 10 份」淘汰，未入队成功的暂存文件不会被主动清理；量大时人工清理该目录即可（不入审批、不写业务库）。
- **导入文件 rev 高于当前快照**：D4-2 的 `max(cur, incoming)+1` 在同进程 `casWrite`（固定 `curRev+1`）下等价于 `curRev+1`（仍单调不回退）；回执里同时记 `incoming_rev` 供审计甄别这类异常来源。
- **既有历史失败**：算法层存在 `dish.test.js` / `dish_import_delete.test.js` 两例历史失败，与本 ADR 无关，不要顺手改。
- **报价数据为空**：当前 `data.quotes` 为 0 条。W2-02/03 的端到端验收已由 `scripts/verify-adr013-batch1.js` 在**隔离 BFF + 自造样例报价**下覆盖（不污染真实快照）；W2-04（导入比价结果）落地时沿用同一套路。
- **红线基线补登记**：Phase 2 `merge.js`（`vendor_terms` 并入 `COLL_KEY`）当时漏刷 `ci/redline_baseline.sha256`，导致 R3/R4 自 2026-10-28 起持续报红；第 1 批收尾时补登记并重算哈希，记录见 `docs/治理与待办/redlines.md` §6。**后续任何底座文件改动须同批刷哈希并在该表登记**。
