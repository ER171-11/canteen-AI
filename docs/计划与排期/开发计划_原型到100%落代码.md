## 1. 目标与范围

### 1.1 目标

把 `熊猫五福App原型.html` 中的全部可交互形态（5 个主 Tab + 12 个经营模块 + 厨房 4 子页 + 进销存 4 子页 + 6 处 Kimi 拍照 + 确认台抽屉 + 桌台并/拆单撤销栈 + 预测置信滑块 + 五色寓意）逐屏翻译为可在真机运行、可评审、可灰度发布的**生产级双端原生 App**，并完成与云端 BFF、店内进销存、Kimi 视觉的端到端打通。

### 1.2 技术栈选型（对齐 PRD v1.0 §6.1）

| 层 | 选型 | 说明 |
|---|---|---|
| iOS App | Swift + SwiftUI（UIKit 兜底） | 原生体验；SwiftUI 优先，复杂自绘（热力/矩阵）用 UIKit `Canvas` |
| Android App | Kotlin + Jetpack Compose | 原生体验；自绘用 `Canvas`/`DrawScope` |
| 双端共享 | Kotlin Multiplatform（KMP）共享业务/数据层 | UI 各自原生；Repository/ViewModel/DTO/网络层走 KMP |
| 云端 BFF | Node（零依赖内置模块，复用 `bff/server.js` 已跑通实现） | 已含 `/api/kimi/vision` + SSE `/vision/stream` + 6 prompt + 降级矩阵 |
| 店内进销存 | Python（与 server/ 同栈）+ SQLite（主，零改动） | 在既有 12 模块上**做加法**：快照推送器、队列消费器、AI 决策层、菜谱/SOP 引擎 |
| AI 视觉 | Kimi / Moonshot 视觉模型（kimi-* 推理家族） | 经 BFF 代理；Key 仅 env |
| 厨师 SOP 端 | 厨房平板 H5 嵌入 App WebView 或店内浏览器 | 低成本、易更新 |

### 1.3 "100% 落代码"完成定义（DoD）

| # | 验收门 | 判据 |
|---|---|---|
| D1 | 原型 5 主 Tab + 12 模块全部有原生对应屏 | iOS/Android 各自 100% 屏覆盖，交互态（状态机/撤销栈/滑块）等价 |
| D2 | 6 处 Kimi 拍照端到端打通 | 拍照 → BFF → Moonshot → kimi-card 渲染 → CTA 走确认台，SSE 流式可视进度条可复现 |
| D3 | 写回闭环端到端 | App 确认 → 云端队列 → 店内消费器 → `/api/sync`（带 rev）→ 快照回写"已执行"，状态机四态完整 |
| D4 | 红线零破坏 | `rebuildStock`/`dishRecipeCost`/`seedDB` 全程零改动；AI 不直接写库；结算单只读；新增表与红线解耦——红线回归测试全绿 |
| D5 | 只读先行落地 | P0 模块只读看板可验收；数据时延 ≤15 分钟且 UI 明示 |
| D6 | 双端一致 | iOS/Android 共享 KMP 层，UI 行为差异 ≤5%，关键交互一致 |
| D7 | 灰度可发布 | TestFlight + 内测分发通道就绪；快照推送灰度策略可配 |
| D8 | 可观测 | 全链路 traceId 留存 30 天；快照推送/队列消费/对话调用日志齐全 |

### 1.4 非目标（不做，对齐 PRD v1.0 §1.5）

- 不替换现有进销存系统，不重写计价/成本/库存重放核心。
- 不做连锁/多店架构（单店）。
- 不做 C 端顾客点餐小程序。
- 不让 AI 自主下单/改库存。
- 不用大模型直接算毛利/成本。

## 4. 数据模型与契约

### 4.1 DB 增量表 DDL（仅增不改，对齐 PRD v1.0 §7 + 任务清单 S8）

> 全部与既有 `dishes/ings/sales/orders/recv` 外键关联，**不改既有字段**；新增表不得与 `rebuildStock/dishRecipeCost/seedDB` 逻辑耦合。温度高频写入独立时序表，不进主 DB 的 rev 合并（任务清单 M8-T1）。

| 表 | 关键字段 | 关联 | 期 | 红线 |
|---|---|---|---|---|
| `recipes` | `sku_id PK, name, color, filling, face_main(JSON), main(JSON), aux(JSON), seasoning(JSON), steps(JSON), params(JSON), blessing, diet_tags(JSON), version, updated_at` | → `dishes` | P0 | 仅增；色源字段锁定 |
| `sop_steps` | `sku_id, step_no, stage(和面/醒发/备馅/拌馅/剂子/包制/煮制/装盘), duration_min, tools, inputs(JSON), key_points, qc_point, risk, params(JSON)` | → `recipes` | P0 | — |
| `sop_workorders` | `date, sku_id, qty, planned_start, status(待开始/进行中/已完成), qc_records(JSON)` | → `recipes` | P0 | — |
| `qc_records` | `workorder_id, sku_id, sample_weight, pass, ts, source(manual/kimi)` | → `sop_workorders` | P0/P1 | Kimi 仅识别，写需确认 |
| `actions_queue` | `id PK, type, payload(JSON), status(待执行/已执行/已驳回/已过期), rev, created_at, executed_at, operator, trace_id` | → `/api/sync` | P2 | 写回带 rev；防重 |
| `snapshot_rev` | `rev PK, generated_at, size_bytes, module_mark(JSON)` | 只读副本元数据 | P0 | 仅推 JSON+rev，<5MB |
| `kimi_log` | `trace_id PK, type, user_id, model, http_status, dt_ms, degraded(bool), usage(JSON), ts` | 审计 | P1 | 留存 30 天；不含 Key/图 |
| `forecast` | `date, sku_id, qty_pred, confidence, band_low, band_high, model_ver, created_at` | → `recipes` | P1 | 预测 ≠ 下单（UI 强制确认） |
| `pos_tables` | `table_id PK, name, capacity, status(空闲/用餐/待清/预订), cur_order_id, locked_until` | → `pos_orders` | P0 | 桌台四态 |

| `pos_payments` | `order_id, method(微信/支付宝/现金/储值), amount, ts, rev` | → `pos_orders` | P0 | 混合支付各成分≥0 合计=应收 |
| `pos_hanging` | `order_id, creditor, amount, due_date, status(挂账/冲销), rev` | → `pos_orders` | P0 | 挂账进应收不进实收 |
| `undo_stack` | `session_id, seq, op_type(并单/拆单/状态变更), before(JSON), after(JSON), ts, reverted(bool)` | 端侧本地（SQLDelight） | P0 | 撤销栈；历史回跳 |
| `staff_shifts`/`staff_clock`/`staff_perf`/`staff_train` | 见 PRD v1.1 §2 | 既有员工档案 | P0 | 换班写回带 rev |

## 9. 红线工程保障（如何在代码层强制）

> 对齐 PRD v1.0 §1.5/§6.4、PRD v1.1 红线复述、Kimi 契约 §7、任务清单§七。

| # | 红线条款 | 工程化手段 | 落地位置 |
|---|---|---|---|
| R1 | AI 只读不写 DB | BFF 层拦截：`/api/kimi/vision` 与 `/api/agent/chat` 路由无写路径；写路径仅 `/api/actions*`，且必经确认 | `bff/routes/` + 中间件 |
| R2 | 写回带 rev 乐观锁 | `actions_queue` 表 `rev` 字段非空；`/api/actions/{id}/confirm` 必带 `rev`；消费器调 `/api/sync` 带 `base_rev` | `store-inventory/queue_consumer.py` |
| R3 | 计价与三向合并核心零改动 | 共享库封装：`CoreProtected` 模块只暴露只读接口；git diff 守卫脚本断言 `rebuildStock`/`dishRecipeCost`/`seedDB` 文件无变更 | CI 红线回归 + `store-inventory/server/app.py` 不动 |
| R4 | 受保护函数零改动 | 同 R3；新增表与受保护逻辑解耦校验脚本 | CI |
| R5 | Key 仅 env 不入 git | BFF `process.env.KIMI_API_KEY`；`.env` 入 `.gitignore`；CI 扫描代码中无硬编码 Key | `bff/server.js` + CI secret scan |
| R6 | 预测 ≠ 下单 | UI 强制确认按钮：`ForecastConfSlider` 后必接 `ConfirmSheet`；无"直接下单"路径 | `apps/*/ForecastConfSlider` + KMP `ConfirmGateway` |
| R7 | 结算单只读输出层不写 DB | 结算单数据来自 `DB.recv`，模板存独立 localStorage；BFF 无结算单写端点 | `bff/routes/`（无该写端点） |
| R8 | 色源锁定 | `recipes` 表色源字段只读；Kimi `recv`/`stock` prompt 明确色源锁定；识别到非火龙果色源标"色源异常"警告 | prompt + BFF 校验 |
| R9 | 自动生成 ≠ 自动下单 | `stock` 用例 `生成补货单` 仅为建议；`actions_queue` 入队前 status=`queued`，需确认才转采购 | `ConfirmGateway` |
| R10 | 图片不落库 | BFF 图片 base64 仅内存传 Moonshot，响应后销毁；不写 SQLite、不写快照 | `bff/lib/moonshot.js` |
| R11 | LLM 不直接算账 | `/api/agent/chat` 路由只调确定性函数取数 → LLM 生成；不传毛利/成本计算给 LLM | `bff/routes/agent.js` |
| R12 | 隐私（着装不存人脸） | `uniform` 用例仅返回合规判定；不存储人脸/原图 | prompt + BFF |

> **守卫层级**：代码层（接口/类型）→ BFF 层（路由拦截）→ DB 层（rev/约束）→ CI 层（红线回归）→ 发布层（灰度门）。四层联防。
