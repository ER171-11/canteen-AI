## 1. 背景

- 旧系统是**单文件 HTML**，跑在店内电脑上，**只有店内一个入口**：录入即直写本地库并 `saveDB()`。
  证据：FP-RECV-01 `HTML:299 #btnNewRecv` → `openRecv()` `HTML:1663`，其选项为 `{stockIn:true}`（保存即入库）；
  删除 `delRecv()` `HTML:1676` 直接物理移除并按剩余单据重建台账。
- 替代模式下（`docs/迁移颗粒度规范.md`），旧 HTML 已归档到 `old/store-inventory-legacy/`（只读证据），
  新架构是「云端 BFF + `admin-web` + 双端 App + 店内 Node 节点」。于是「进货单到底在哪里录」必须重新回答。
- **店内节点当前没有任何可用的录入界面** —— 这是本决策的硬前提：
  - `bff/store-node/server.js:40`：`serve_static: false`。
  - `bff/store-node/server.js:81-82` 注释原文：「旧配置里的 `serve_static` 属于**已退役 HTML**，除非本目录显式覆盖，否则关闭」。
  - `store-inventory/server/config.json:9-11` 仍写着 `serve_static: true` + `index_file: 熊猫五福餐厅进销存系统_真实数据版.html`，
    但该 HTML 已归档，`store-inventory/` 下**并不存在** → 即使强行启用也只会 404。
  - `scripts/dev-up-native.sh:36` 店内节点的启动方式是**无头服务**：`node bff/store-node/server.js --port 8765 --db <...餐厅系统.db>`，
    对外只有 `/api/health`、`/api/db`、快照与队列接口。
- 所以本题不是「两个界面之间选哪个」，而是「**复用已有界面**」还是「**先造一个界面**」。
  且 FP-RECV-01 是 T6 的阻塞项（未定边界不得动代码），必须先把边界定下来。

## 2. 决策

**选择 A：云端 `admin-web` 为唯一写入口。**

1. **唯一写入口**：所有进货单写操作（新建 / 编辑 / 作废 / 批量导入）一律走
   「建议动作 → `POST /api/actions` 入队 → 审批 `confirm` → 店内消费器执行 → 三向合并回写」，
   **不新增第二条写通道**（落实红线 ③⑤「写回必经确认 + 队列 + rev」「后台禁止旁路写」）。
2. **现场录入形态**：店内电脑用**局域网**打开同一套 `admin-web`（`scripts/dev-up-lan.sh` 已存在），
   与远程录入**共用同一界面、同一条队列、同一套审计**。**不新建店内录入界面。**
3. **动作类型**：新建沿用已注册的 `recv.inbound`；新增并注册 3 个：
   - `recv.update` —— 编辑进货单（FP-RECV-08）
   - `recv.void` —— 作废进货单（FP-RECV-09）
   - `recv.import` —— 批量导入提交（FP-RECV-02），payload 携带整批明细
   `bff/store-node/consumer.js` 对**未注册**的 type 会判 `need-manual` 驳回，故「在 registry.js 注册」是硬要求，不是可选优化。
4. **批量导入的原子性与性能**：预览阶段纯计算、**不产生任何写**；提交阶段**只入队一个** `recv.import` 动作，
   因此整批只推进 `rev` 一步、批内原子。执行器内部复用单张单据的写入步骤，**批末统一 `stock.rebuildStock` 一次**，
   避免 N 次全量重算——复杂度由 O(N × 库存行数) 降为 O(单据数 + 库存行数)。
5. **作废语义**：标记 `status = '已作废'` 并记录作废人 / 时间 / `rev`，**保留原单据行**。
   旧版 `delRecv`（HTML:1676）的**物理删除**不得照搬——它会让「谁在什么时候作废了哪张单」永久不可考。
6. **`rev` 语义不变**：仍是乐观锁、先到先得；冲突时 `confirm` 返回 `409`，让用户刷新重来。
   店内节点**不因「人在现场」而获得覆盖权**。

## 3. 为什么不是别的方案

| 备选 | 否决理由 |
|---|---|
| **B：店内系统为唯一入口** | ①**店内没有界面可复用**（§1），等于把一个前端模块从零做起；②须新开一条「接受店内直录结果」的上报通道，`POST /api/actions` 不再是唯一写入口，红线 ③⑤ 需豁免；③FP-RECV-08/09 按基线**必须**走队列，于是「新建在店内、改删在云端」——B **必然退化为最贵的 C** |
| **C：双入口（云端录 + 店内录）** | 同一条单据有两条写路径：`rev` 冲突面扩大；审计要合流两套 `operator`；权限要维护两套登录态。且「云端已批准但尚未执行」的动作与店内直录结果谁优先，需再造一套裁决规则（作废丢弃还是暂存重放） |
| 店内放一个「瘦客户端」只把表单转发给云端队列 | 与 A 效果相同但多一跳部署与故障面。店内电脑本来就只需一个浏览器就能打开 `admin-web`，没必要再引入一个常驻转发进程 |
| 把 `admin-web` 打进店内节点静态目录（打开 `serve_static`） | 把前端发版与店内节点发版绑死；店内节点是零依赖无头服务，引入静态资源服务面会扩大攻击面。需要「不依赖外网」时，改用局域网访问 BFF 即可 |

> 被否决方案共同的核心代价：**打破「队列是唯一写入口」**。一旦打破，`rev`、审计、权限三件事都要重做一遍。

## 4. 保了什么（意图层，不可让）

| 项 | 保障手段 |
|---|---|
| 写类不直写库 | 全部经 `/api/actions` + 审批 + `rev`；`ci/redline_guard.sh` 的 R13 静态扫描后台旁路写（直连 `/api/sync` / sqlite / `.db`） |
| 作废留痕、不物理删 | `recv.void` 只改状态并写审计；`applyRecvVoid` 内不出现 `DELETE` |
| 批量导入不可半途落库 | 预览阶段零写；提交只入队一个动作，批内原子 |
| 旧版录入字段不缩水 | 表单字段对照旧版 `openRecv`（供应商 / 日期 / 明细：原料·订购量·实收量·单价·金额 / 实付 / 欠款 / 关联采购单）逐项对齐 |
| 库存口径不漂移 | 执行器末尾统一调 `stock.rebuildStock`，与既有 `applyRecvInbound` 同一口径（红线 ①：只可调用不可改写） |
| 越权不可写 | 服务端 `auth.WRITE_ROLES` + `mayWriteActions` 为权威；前端 `canWrite` 只是体验层 |
| 现场可录可查 | 店内电脑经局域网打开 `admin-web`（`scripts/dev-up-lan.sh`） |

## 6. 如何验证

```powershell
cd bff; npm test                                   # 含 actions/consumer/registry 与 recv_* 执行器用例
node bff/store-node/run-tests.js                    # 店内节点
node bff/store-node/seed/run-tests.js               # seed 平价（Node↔Python 差分）
cd apps/admin-web; npm run lint; npm run build      # ESLint（--max-warnings 0）+ 类型 + 构建
node scripts/lint-zero-dep.js                       # 后端零依赖静态检查
powershell -NoProfile -ExecutionPolicy Bypass -File ci/redline_guard.ps1   # 红线守卫（本机）
powershell -File scripts/gen-debt-table.ps1 -Check  # 基线/欠账总表漂移
```

人工验证（**必做，不可由门禁代替**）：

1. 店内电脑（或同一局域网另一设备）打开 `admin-web` 的进货入库页，能正常录入 —— 验证 §2.2 的现场形态成立。
2. 新建一张 JH 单 → 审批中心确认 → 店内节点的库存与欠款按 `rebuildStock` 口径变化，且全程状态可见。
3. 编辑 / 作废各一次：作废后原单据**仍在列表可见且标记为已作废**，审计里能查到操作人与时间。
4. 批量导入：故意在文件中留一行非法数据，确认**预览阶段即报错且库中零变化**。

## 7. 副作用与遗留（需后续处理）

| # | 遗留 | 影响 | 建议 |
|---|---|---|---|
| 1 | 「店内现场录入」的实际体验**未做人工验证** | 本决策假定「店内电脑有浏览器 + 局域网可达 BFF」。若现场无浏览器或网络不通，本 ADR 需重新评估 | 按 §6 人工验证第 1 条实测；不成立则重开 B/C 评估 |
| 2 | A 的**中间态时延**（入队 → 待执行 → 已执行） | 期间店内看到的库存是**旧的**。若有人据旧库存决策，可能误判 | 前端以状态徽标显式告知（既有模式），**不得隐藏中间态**；必要时在页面上明示「N 张动作待执行」 |
| 3 | 审批人不在场时动作悬挂 | 队列堆积、库存停更且无人察觉 | 属既有运行保障层问题（见 `docs/运行保障层.md`），不在本 ADR 范围；当前靠看板/C I 门禁暴露 |
| 4 | 导入解析的格式覆盖度 | 旧版支持 xlsx / 伪 xls / html / csv 四种。零依赖自写解析不可能 100% 覆盖 | 支持范围与**明确不支持**的格式须在界面上写清，**不得静默降级**（红线 ⑥） |
| 5 | `applyRecvInbound` 的 `items` 分支是 **Node 超集**：`paid` / `method` / `po` / 行内 `recvQty` 在 `queue_consumer.py` 中**没有对应实现**（旧版这三项只在浏览器 JS 的 `openRecv`，旧 HTML:1636-1654） | 该分支因此**无 Python 侧可差分**，只能靠行为契约测试锁（`bff/lib/algorithms/recv_inbound.test.js`，11 例）；超集字段全部可选，不传时输出与 Python 逐字段一致（用例 7 专守） | 若后续要恢复「算法层 100% 可差分」，需把这三项回移进 Python 侧或正式登记为「有意偏离」（已在 `docs/Python到Node忠实性映射表.md` §1 补注登记） |
| 6 | 旧版「关联采购单」会经 `syncAllOrderRecv()` 回写采购单**收货进度**，Node 侧**未实现** | 本版只登记单向关联 `recv.po`；采购管理页的收货进度（订单行 `recvQty`）不会因新建进货单而变化 | 属采购管理页欠账，随 `FP-采购管理.md` 相关行落地；界面上已明示该差异，不做静默假装 |

## 8. 回档方案

- **逻辑回档**：把 `registry.js` 中新增的 3 个动作类型注册移除，消费器即对 `recv.update` / `recv.void` / `recv.import` 判 `need-manual` 驳回，
  前端相应入口隐藏即可——已入队但未执行的动作会停在队列里等待人工处理，**不会造成静默的错误落库**。
- **代码回档**：本 ADR **不触碰** `bff/store-node/{db,merge}.js`（哈希基线受保护文件），也不改数据库 schema，回档无数据迁移成本。
- **已作废单据**：`recv.void` 只改状态不删行，故回档后数据完好在位；不会出现「回档即丢单」。
