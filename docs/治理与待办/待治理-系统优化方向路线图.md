## 0. 现状概览

系统当前已较成熟：

- **功能层**：FP 基线 151 项中已移植 136 项，剩 **11 张欠账卡**（W2 4 / W3 4 / W4 3）。
- **底座能力**：审批队列 / 写操作幂等 / 红线守卫 / schema 版本化 / 桌面端自动更新（electron-updater）均已落地。
- **架构**：主存是**每台终端本地的 `snapshot.json`**（桌面端 BFF `CANTEEN_LOCAL_APPLY=1` 直接落盘；`store-node` / SQLite 四件套在桌面端**休眠未运行**），真正的偏离是「账本分散在终端、无中心化」；ADR-009 已定「服务端为真」，ADR-010 已拍板迁「腾讯云 PostgreSQL 单一主存」，但代码尚未动（详见 ADR-010 §2、§6）。

本文按**杠杆从高到低**列出可继续优化的方向，每条附现状依据、价值与建议。

## 一、架构底座（最高杠杆，当前最大技术债）

### 1.1 落地 ADR-010（云端单一主存，**已拍板、待执行**）

- **现状依据**：`docs/decisions/ADR-010` **已拍板 D0–D3（2026-10-28）**，且 **Phase 0 接缝层已于 2026-10-28 完成**（`store-adapter/{index,json,sqlite,pg}` + `action-runner` + 独立 `worker` + 契约测试 json/sqlite 双绿，已接入 `npm test`）。**运行时主存形态未变**：仍是每台终端本地 `snapshot.json`（默认 `STORE_ADAPTER=json`，等价旧实现），账本**分散在终端、无中心化**，`snapshot.json` 无事务 / 多写者语义（乐观锁现由适配器层 `casWrite(rev)` 补上），撑不起多店中心主存。原「底座倒挂」的说法已被 ADR-010 §2.1 修正：`consumer.js` 写 `docs.data` + 60 余张 ext 业务表的那条链路在桌面端**休眠未运行**，不是生产账本。
- **已拍板决策**（ADR-010 §5，不再待定）：
  - **D0** 建远程中心服务，云端落**腾讯云**。
  - **D1** **腾讯云托管 PostgreSQL**（每店一行 `data JSONB` + `rev` 列做乐观锁；备选 TDSQL-C PostgreSQL）。**不选自管 SQLite**。
  - **D2** **独立 worker 进程**轮询 DB 队列落库，BFF 只入队 / 审批 / 读；v1 单 worker，不引入 SCF / TDMQ / K8s。
  - **D3** **按店粒度**迁移历史 → 切流后只写云端，**严禁双写**；**断网按 ADR-010 §9 沿用 ADR-009 §2.1 只读**（localStorage 热备、过期即弃，不做离线写）。
- **价值**：后续写类执行器（销售/采购）不再在「终端本地主存」上叠层；顺带解除 R3/R4 哈希锁。
- **建议**：Phase 0 已就绪（红线五项已在本地验完、契约测试 json/sqlite 双绿），下一步只等**腾讯云权限**做 Phase 1 建库 → Phase 2 迁移切流 → Phase 3 本地退场（ADR-010 §6、§7）；期间运行时继续跑本地 json 适配器，**不做任何存储切换**。

### 1.2 跨端数据同步（ADR-011 留的口子）

- **现状依据**：`ADR-011` 末尾明确「终端本地主存（`snapshot.json`）→ 云端 → 桌面的跨端数据同步仍是 ADR-010 的后续项」，本 ADR 仅解决「升级不丢数据 + 检查更新」。
- **价值**：云端主存落地后，桌面端首次启动拉全量、后续增量同步的机制补齐，才能形成完整闭环。
- **建议**：在 ADR-010 完成后再设计，避免提前做重复工作。

## 二、业务功能收口（最直接可见价值）

### 2.1 清空剩余 11 张欠账卡

依据 `docs/迁移基线/欠账总表.md`，11 张卡当前「负责人」全为「待指派 + 建议角色」，落地前需替换为真人（规范 §3 要求）。按风险分组：

**W2 · 业务闭环（4 项，低风险）**
- `W2-01` `FP-SET-10` 快照列表查看与回滚（回滚高危，须留痕）。
- `W2-02` `FP-PRICE-07` 删除某条报价记录（`quote.delete` 走审批队列，执行器已登记，非阻塞）。
- `W2-03` `FP-PRICE-11` 生成并下载「待比价任务」JSON（只读导出，不写库）。
- `W2-04` `FP-PRICE-12` 导入「比价结果」JSON（按 conv 折算、去重追加，批量建议动作入队）。

**W3 · 录入类（4 项，需走审批队列）**
- `W3-01` `FP-ING-05` 手工校准库存/均价并自动生成「手工调整」流水（须留痕）。
- `W3-02` `FP-ING-06` 批量设置安全库存/出成率（一屏多原料）。
- `W3-03` `FP-ING-11` 删除原料（**带引用保护**：已用于单据/配方则禁删）。
- `W3-04` `FP-ING-13` 原料行「比价」入口（录入/查看报价 + 跳转外部平台搜索）。

**W4 · 高危与待决策（3 项，最高危）**
- `W4-01` `FP-SET-15` 导入 JSON 备份恢复（全覆盖）——**双人确认 + 审批队列**。
- `W4-02` `FP-SET-16` 重置为真实数据基线（海南菜篮子采购单）——**强制先自动备份**。
- `W4-03` `FP-SET-17` 清空全部业务数据——**强制先自动备份**。
- **建议**：W4 三项风险最高，建议放在最后且单独评审，必须绑定「强制自动备份 + 双人确认 + 审批留痕」三道防线。

## 三、数据与主数据治理（影响所有报表口径）

### 3.1 原料主数据收口

- **现状依据**：`docs/治理与待办/待治理-原料主数据与低值易耗品同库问题.md`。`type` 语义分层（food/consumable）+ 五处口径过滤已代码落地（主库 rev 280、163 项），但**剩的全是人工收口**：
  - 19 项错位 `cat` 归位（芹菜→蔬果、炮笋鱼/鲜鱿鱼→冷链、鲁花芝麻油等→干调类…）。
  - 新建 62 项食材暂落「其他」，需补填 `cat/buy/conv/safe` 四列。
  - `cat` 枚举收敛（蔬菜类→蔬果、鲜肉类→肉类、水产类→冷链）。
- **两个更深未解问题**（比单纯归位更优先）：
  - **`conv` 换算失真**：`conv` 恒为 1、规格写进名称（`1件*24罐`、`5斤/包`），导致入库数量失真 → 库存/成本/损耗全错。
  - **无别名/同义词机制**：`findIng` 仅精确匹配，已造成「鲁花芝麻油350ml」重复建料。
- **价值**：这是所有成本/损耗/比价报表正确的前提，是数据质量的真源头。
- **建议**：先解决 conv 换算 + 别名机制（代码层），再做人工归位与四列补填。

### 3.2 报表口径一致性实证

- **现状依据**：同 3.1 文档 §4「影响面盘点」明确标注"未逐条实证"——成本/损耗/比价/补货/经营分析是否真按 `isFood` 过滤全对，没有断言保障。
- **建议**：补一组回归断言，确认真实报表不会被耗材污染。

## 四、工程效率与防漂移

### 4.1 桌面端双副本同步的漂移风险

- **现状依据**：`desktop/scripts/sync-assets.js` 把 `bff/` 镜像进 `desktop/app/bff/`，靠 **mtime 时间戳比对**（差异 `>1000ms` 才判变更）。但 `schema.js` 需「两端手动同步」、`algorithms/sale.js` 是**同步副本**而非自动同步——发版链路里人工漏同步，会让桌面端跑旧算法而无报错。
- **价值**：消除「改了没同步」的静默事故（最危险的一类，因为无报错、难排查）。
- **建议**：二选一——
  - 构建期硬校验：两端关键文件 diff 不一致即 `process.exit(1)`；
  - 或把 `sync-assets.js` 的 mtime 比对改为**内容哈希**比对。

### 4.2 移动端契约一致性

- **现状依据**：`apps/android-app` / `apps/ios-app` + `kmp-shared`（KMP 共享层）与 BFF 的接口契约，目前未见契约测试。BFF 改字段（如 ADR-011 的 schema 迁移）时，移动端是否同步收口没有自动护栏。
- **建议**：补一份 BFF ↔ KMP 的契约测试，作为发版门禁。

### 4.3 算法层「无关失败」清零

- **现状依据**：算法层长期为 23/25，两个 `dish` 用例「无关失败」（记忆登记为既有、无关）。
- **风险**：测试噪声会掩盖真回归，使 `npm test` 全绿失去门禁意义。
- **建议**：定位并清零这两个失败（很可能是用例自身预期过期），让 `npm test` 回到真全绿。

## 五、可观测性与现场验证

### 5.1 断网降级现场实测

- **政策已定（2026-10-28）**：ADR-010 §9 拍板——断网**沿用 ADR-009 §2.1 只读**（localStorage 热备、过期即弃），**不做离线写**；若将来要求离线可写须另立 ADR。故实测范围也随之收窄为「只读降级体验 + 恢复后队列自动续跑」，**不含离线开单/记账**。
- **现状依据**：`docs/治理与待办/待治理-审批中心语义澄清与状态枚举双轨.md` §4.2，ADR-004 §7.1「店内现场录入未人工验证」仍是**敞口**，只登记未关闭。断网不丢数据（动作停队列、24h 才过期），仅为时延，但"店内浏览器 + 局域网实测"尚未执行。
- **建议**：用真实店内环境跑一轮「断网 → 只读可用 → 恢复自动续跑」，把敞口关闭。

### 5.2 红线 / 审计可视化

- **现状依据**：SI 政策自动放行（`maybeAutoExecute`）默认 `auto_enabled=false`，有审计（`siAudit.log`）+ 可回滚（`saveRollback`），但**无可视化看板**。这正是 ADR 里澄清过的「审批中心命名易误解」语义风险点。
- **建议**：审批中心增加「自动放行记录」视图，避免"绕过审批"误读。

### 6.2 发版自检脚本化

- **现状依据**：发版 SOP 含一串发版后自查（curl `releases/latest` 返回新版本号、Release 资产含 `canteenAI-Setup-<ver>.exe` + `latest.yml` + `.blockmap`），目前靠人工记忆。
- **建议**：固化成 `scripts/verify-release.js`，发版流程一键跑，替代人工记忆。

## 七、推进顺序建议

| 阶段 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **P0** | ~~ADR-010 Phase 0 接缝层~~ **✅ 已完成（2026-10-28）**：`store-adapter` json/sqlite/pg + `action-runner` + 独立 `worker` + 契约测试双绿；默认仍 json，运行时读写行为不变 | 无（无需云权限） | — |
| **P1** | 并行收口低风险欠账：W2 全清 + W3 四项（替换"待指派"为真人） | 无 | 低 |
| **P2** | 原料数据质量：conv 换算 + 别名机制（代码层） | 无 | 中 |
| **P3** | ADR-010 **Phase 1–3**（建库 → 迁移切流 → 本地退场）+ 桌面端防漂移改造（4.1） | P0 + **腾讯云权限 + 业务窗口** | 高 |
| **P4** | W4 高危三项 + 断网实测（5.1）+ 发版自检脚本化（6.2）收尾 | P1/P3 | 中（W4 高危） |

> 原则：**先做接缝（P0，无云权限即可开工），再收低风险业务（P1），同步治数据源头（P2），拿到云权限后做底座迁移（P3），最后高危与现场验证收尾（P4）**。避免在「终端本地主存、无中心化」的底座上继续叠加写类功能。
