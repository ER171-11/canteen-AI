# ADR-007：结构测算「模拟态」的只读推演边界

- 日期：2026-09-30
- 状态：已实施
- 关联：ADR-002（去 Python 架构收敛）、ADR-003（进货单/写回口径）、ADR-006（写操作幂等边界）
- 影响面：`bff/lib/menu_baoben.js`、`bff/routes/analysis_sim.js`（新增）、`bff/server.js`（仅注册）、`bff/routes/modules.js`（仅接入口径参数）、`apps/admin-web/src/pages/ops/*`、`apps/admin-web/src/api/*`
- 触发：欠账总表「执行前置依赖」—*结构测算「模拟层」设计（只读推演、禁写库）→ FP-CALC-11/12/13 → 设计说明 + ADR*；本 ADR 即该项产物，与实现同日落地
- 备注：全局红线①要求「所有写操作只经 `POST /api/actions` 队列」。模拟层若不设边界，极易被写成「改价先落库再回读」，从而绕过队列。本 ADR 把模拟层显式定义为**纯推演**：既不落库、也不入队，写类意图只允许出现在「建议动作清单」里由人工确认

---

## 1. 背景

旧版结构测算页的量本利推演是**内存态**的：

- `SD[]` 是 `DB.dishes` 的内存副本（旧版 HTML:3845 `syncCalc()`），`calcModel()`（:3923）在浏览器内按 `SD` 重算 `CR`；
- `renderCalc()`（:4247）用 `CR` 重绘 KPI / 参数卡 / 五类角色卡片 / 逐菜表 / 三图 / 建议；
- 全程没有一次写库调用；「按建议改菜品」也仅是把口径数值写回时另行走保存链路。

新版把量本利公式放在 BFF（`bff/lib/menu_baoben.js` `computeBaobenSummary`），页面经 `GET /api/modules/analysis` 取 `baoben_summary`。于是「即时重算」面临一个岔路：

1. **前端复算**——把公式搬到 `apps/admin-web`。这会产出**第二份公式**，与阶段 9 已确立的
   「参数卡/合计一律取后端 `kpi`，不在前端复算」直接冲突，属于必然漂移的架构债。
2. **后端推演**——覆盖值送回 BFF，用同一份公式算，只读返回。

同时，`GET /api/modules/analysis` 所在的 `bff/routes/modules.js` 自身带契约注释：
「只读端点（红线①：只读，无任何写库路径）」，且文件内 `if (req.method !== 'GET') return false;`
（:1495）主动把非 GET 交还外层 404。把 POST 推演塞进该文件会破坏这条契约的自证性。

---

## 2. 决策

### 2.1 新增独立只读推演端点 `POST /api/modules/analysis/sim`

- 落在**新文件** `bff/routes/analysis_sim.js`，由 `bff/server.js` 注册；
- **不动** `bff/routes/modules.js` 的「非 GET 一律不处理」契约；
- 只读 POST 在本仓库**已有先例**：`POST /api/inventory/recv/import/preview`
  （收货导入预览，纯计算零写，`bff/routes/inventory.js`），本端点与它同型。

请求体（全部可选，缺省即「未做覆盖」）：

```
{
  "params":    { ...24 项店参覆盖... },
  "qmode":     "est" | "real30" | "real7",   // 默认 real30，照抄旧版 SC_QMODE
  "qfallback": true,                          // 默认 true，照抄旧版 SC_QFALLBACK
  "rows":      { "菜名": { "c": 12, "p": 45, "q": 18, "on": false } }
}
```

响应体（实测，本仓 2026-09-30）：

```
{
  "ok": true, "sim": true, "rev": "<快照版本>", "basis": "shop_dishes",
  "qmode": "real30", "qmode_label": "近30天真实（日均）", "qfallback": true, "qdays": 30,
  "baoben_summary": {            // 与 GET /api/modules/analysis 的 baoben_summary 同形
    "brand", "source", "count", "basis": "shop_dishes",
    "params": {...}, "kpi": {...}, "types": [...], "scenes": [...], "advice": [...]
  },
  "calc_dishes": [               // 行含 id/name/cat/cost/price/qty/est/sq/src/on
    { "id":"D75", "name":"老虎菜", "cat":"引流", "cost":4.5, "price":18,
      "qty":4, "est":4, "sq":0, "src":"est", "on":true }, ...
  ],
  "qstat": { "n_total": 95, "n_active": 95, "n_real": 5, "n_fallback": 90 }
}
```

> 前端契约（`apps/admin-web/src/api/types.ts` `AnalysisSimResp`）与本表一一对应；
> `kpi` 字段名沿用阶段 8/9 已验收输出（`day_rev`/`be_day`/`month_profit`/…），未增删。

### 2.2 零写库是**可测断言**，不是声明

推演路径只允许出现：`loadSnapshot()`（只读）、纯函数计算。禁止出现：`saveDB`、写 `data/*.json`、
`postAction`、写 `actions_queue.json`。覆盖一律 `Object.assign({}, row, ov)` 生成新对象，
**绝不 mutate** 快照数组与其元素。

落成单测（`bff/lib/algorithms/baoben_sim.test.js`）：连续调用推演前后，断言

- `data/snapshot.json` 的 `mtimeMs` 不变；
- `data/menu-baoben.json` 的 `mtimeMs` 不变；
- `data/actions_queue.json` 的条目数与内容不变。

### 2.3 公式单一来源：抽出 `computeModel(rows, P)`

把 `computeBaobenSummary()` 的算术核心抽成 `computeModel(act, P)`（`act` 为
`{price, cost, qty, type}` 行数组），基线汇总与模拟推演**共用同一函数**；
`computeBaobenSummary()` 保持对外输出逐字段不变，用既有断言锁死防漂移。

### 2.4 模拟态基准行集 = 逐菜表行集（本店在售菜品）

旧版 `calcModel()` 口径是 `SD`（上架菜品，本仓 95 行），而新版基线 `kpi` 口径是保本价盘
（本仓 86 项，价盘 ⊆ 逐菜表，差集为 9 个 `SKU-WF-*` 未定价占位菜）。

**决策：模拟态采用逐菜表 95 行口径**，最忠实旧版；为此接受两点已登记的代价：

- 进入模拟态首帧店级 KPI 跳变（实测，本仓 2026-09-30）：

  | KPI | 基线（保本价盘 86 项） | 模拟态（本店在售 95 行） | 差 |
  |---|---|---|---|
  | `day_rev` 日营收 | 20,552.8 | 27,725.28 | **+7,172.48** |
  | `be_day` 日保本 | 11,903.49 | 11,848.85 | −54.64 |

  故页面必须挂「模拟态 · 本店在售菜品口径」徽标，不得让两个口径的同一数字无声切换；
- 该口径差异记入阶段记录「主动偏离」条目。

> **基线自身的口径裂缝（本 ADR 一并登记）**：基线页的**逐菜表行集**已经是本店在售 95 行
> （FP-CALC-09 对齐旧版 `syncCalc`），其 `Σprice×qty = 24,108.94`；而基线**店级 KPI** 走保本价盘，
> 隐含 `revDish = 17,872`（`day_rev = revDish × (1+bevRatio)`，本仓 `bevRatio = 0.15`）。
> 即基线页内「表合计 ≠ 店级 KPI」是**既有事实**，不是阶段 11 引入的缺陷。
> 阶段 11 的处理方式是**不掩盖、也不静默修数**：基线页脚注显式披露行集口径，
> 用户点「进入模拟态」后表与 KPI 才同源（都取逐菜 95 行）。

**不进模拟态时页面仍渲染基线（价盘口径）**——即模拟态是**显式进入**的，不做首帧无声置换。

---

## 3. 后果

- 前端不再持有任何量本利公式；`apps/admin-web` 只负责把覆盖值送出去、把结果画出来。
  成本率 / 日营收 / 日毛利额**一律取后端回传行**，前端不复算（升/降级也只改展示口径）。
- 页面「即时重算」= 一次本地 BFF 推演（毫秒级）；行内输入做 **300ms 去抖合并**
  （`WeeklyReportPage.tsx` sim 效果），过期响应按 `seq` 丢弃。代价：输入后约 0.3s 数值才刷新；
  收益：行值、店级 KPI、图表、建议全部来自**同一个响应**，杜绝两份公式漂移。
- 全局红线①不受影响：模拟层无写入、无入队；写类动作仍只出现在「建议动作清单」里，
  由人工确认后走 `POST /api/actions`。
- 回归风险集中在 `computeModel` 抽取：以「`computeBaobenSummary` 输出不变」的断言兜底。
