## 1. 产品概述

### 1.1 背景与机会

熊猫五福餐厅已具备一套自研的「进销存系统」（Python + SQLite，零第三方依赖，覆盖采购→入库→菜品配方 BOM→销售出库→应收实收全链路，含移动加权平均计价、三向合并双机同步、86 道菜品保本测算）。该系统是扎实的**记账/算账**底座，但存在两个缺口：

1. **老板视角缺位**：系统面向"操作员"（采购/库管/收银），没有面向"老板"的决策入口。老板时间被门店琐事挤占，需要"一句话看懂店、一键拍板"。
2. **配方知识未被激活**：餐厅核心资产「御字牌五福饺子」非遗配方（红/黄/绿/紫/黑/白多色、多馅料矩阵，每色配方到克、工艺到步）目前以文档形式存在，未结构化、未进入生产执行链路。厨师 SOP 靠口传手授，新人培训成本高、出品一致性难保证。

机会：在已有结构化数据底座上，叠加**面向老板的决策 AI**与**面向厨房的配方/SOP AI**，把"数据"翻译成"人话决策"与"可执行工单"，形成「店务算账 + 厨务执行」双闭环。

### 1.2 产品定位

| 维度 | 定义 |
|---|---|
| 产品 | 熊猫五福餐厅 · 老板 AI App（原生双端）+ 管理后台（增强）+ 智能菜谱与厨师 SOP AI |
| 一句话定位 | "你管手艺，AI 管算账与提醒；你定标准，AI 管执行与品控" |
| 核心价值 | 把进销存数据翻译成老板可拍板的决策；把非遗配方翻译成厨师可执行的工单 |
| 竞争壁垒 | 五福文化品牌 + 非遗配方护城河 + 真实成本数据闭环 + AI 决策而非 AI 算账 |

### 1.3 目标用户与画像

| 角色 | 画像 | 主要使用端 | 核心诉求 |
|---|---|---|---|
| 老板（宋子刚类） | 技艺型老板，主理非遗配方，时间被门店琐事挤占 | 老板 AI App（手机） | 离店也能看懂店、少看屏多拍板、异常有人提醒 |
| 店长 | 执行型，守店、对账、补货 | 管理后台（店内电脑/平板） | 操作高效、对账准确、补货不漏 |
| 厨师长/厨师 | 出品型，按配方与 SOP 出餐 | 厨师 SOP（厨房平板） | 按工序出餐不乱、新人能跟做、品控有据 |
| 采购/库管 | 执行型 | 管理后台 | 进货入库、库存盘点 |

### 1.4 核心价值主张

- **对老板**：每日开门即有简报，问题被主动推送，决策只需"确认"。
- **对厨房**：非遗配方结构化入系统，SOP 变工单，新人 3 天能上岗，出品重量/工艺有 AI 抽查。
- **对门店**：配方用量 → 采购用量 → 补货建议 自动贯通，减少断料与积压。

### 1.5 非目标（Non-goals，v1.0 不做）

- 不替换现有进销存系统，不重写计价（移动加权平均）、成本核算、库存重放核心逻辑。
- 不做连锁/多店架构（v1.0 单店）。
- 不做 C 端顾客点餐小程序（与本产品边界不同）。
- 不让 AI 自主下单/改库存：所有写操作经老板或店长"确认"后落库。
- 不用大模型直接计算毛利/成本：业务计算交给本地确定性函数，LLM 只做理解与生成。

## 2. 业务现状与资产盘点

### 2.1 已有系统（进销存 · 零改动复用）

- 技术栈：单 HTML 前端 + Python 标准库 `http.server`+`sqlite3`，`127.0.0.1:8765`，数据 `data/餐厅系统.db`。
- 12 模块：经营概览、原料库存、采购管理、进货入库、补货建议、菜品配方(BOM)、结构测算(只读)、销售收银、外接比价、库存流水、结算单(只读)、数据同步与备份。
- 关键 API（已有，复用）：`GET /api/db`（整库 JSON+rev）、`PUT /api/db`、`POST /api/sync`（三向合并写入，带 rev 乐观锁）、`GET /api/snapshots`、`POST /api/rollback`。
- AI 协作红线（AGENTS.md）：`rebuildStock()`、`dishRecipeCost()`、`seedDB()` 为受保护逻辑，禁止 AI 覆盖。本 PRD 全程遵守。

### 2.2 业务资产（御字牌五福饺子 · 非遗配方）

主理人宋子刚（宫廷御膳传人、中国药膳大师）。五色对应五福（长寿/富贵/康宁/好德/聚财）。SKU 矩阵：5 色面皮（红/黄/绿/紫/黑）+ 白色面皮多馅料，详见附录 A。每 SKU 含：面主料、主料、辅料、调料、制作方法（20 步左右）、关键工艺参数（醒发 30 分钟、剂子 10–11g、成品 25–27g、分三次点凉水、料水分三次加入等）。

### 2.3 缺口分析

| 缺口 | 现状 | 目标 |
|---|---|---|
| 老板决策入口 | 无 | 原生 App：简报/对话/一键确认 |
| 配方结构化 | docx 文档 | 结构化入库，可被算账与 SOP 复用 |
| 厨房执行 | 口传手授 | 工单化 SOP + AI 品控抽查 |
| 远程访问 | 仅店内 127.0.0.1 | 上云快照 + 云端 BFF |

### 3.2 三端分工

| 端 | 形态 | 用户 | 联网 | 主要职责 |
|---|---|---|---|---|
| 老板 AI App | iOS(Swift)+Android(Kotlin) 原生 | 老板 | 必须上云 | 简报/对话/一键确认 |
| 管理后台 | 已有 HTML（店内）+ 增强 tab | 店长/采购/库管 | 店内为主 | 进销存操作、AI 配置、店务日历 |
| 厨师 SOP | 厨房平板嵌入（H5 或 App 内 WebView） | 厨师 | 店内为主 | 工单/计时/质检/培训 |

### 3.3 数据流与写回闭环（关键设计）

- **读流**：App → BFF → 只读副本（定时快照，存在分钟级时延，App 明示"数据更新时间"）。
- **写流（确认闭环）**：App 点"确认"（补货转单/结算审批）→ BFF 收为"确认动作"入云端队列 → 店内队列消费器拉取 → 调 `/api/sync`（带 rev 乐观锁）落库 → 下次快照回写 App 可见"已执行"。
- **状态机**：待执行 → 已执行 / 已驳回 / 已过期。
- 红线：写仍走现有三向合并 rev 机制，计价与库存重放核心零改动。

## 4. 功能需求

### 模块一：老板 AI App（原生双端）

#### 4.1.1 每日开门简报（P0）

| 项 | 内容 |
|---|---|
| 描述 | 老板每日早晨收到一条卡片式简报，无需打开 App 即可速览 |
| 触发 | 每日定时段（可配置，默认 08:00）推送 |
| 内容 | 昨日营收/毛利/单量、今日补货待办数、临期原料预警、美团待结算金额、今日计划出品 SKU |
| 数据来源 | 经营概览、补货建议、原料库存、销售收银（只读） |
| 交互 | 点击卡片进入详情；详情内"去确认"跳一键确认台 |
| 验收 | 简报准确反映昨日数据；数据更新时间标注清晰 |

#### 4.1.2 AI 对话（P1）

| 项 | 内容 |
|---|---|
| 描述 | 老板用自然语言提问，AI 返回结构化卡片（图表+结论+建议） |
| 典型问题 | "昨天哪个色毛利最低""火龙果汁还能做几天红色饺子""上周补货有没有超采" |
| 实现 | LLM 做意图识别与生成；业务数据查询调用本地确定性函数（结构测算/库存/补货） |
| 输出 | 卡片：数据表/趋势图 + 结论 + 建议动作（可点"确认"） |
| 红线 | AI 不自行算账，只调函数取数；不直接写库 |

#### 4.1.3 一键确认台（P2）

| 项 | 内容 |
|---|---|
| 描述 | 列出待老板确认的事项，点"确认"即异步落库 |
| 待办类型 | 补货转单、结算单审批、异常处置 |
| 闭环 | 确认 → 云端队列 → 店内消费器 → /api/sync 落库 → 回写"已执行" |
| 防重 | 状态机+rev 乐观锁；同一动作不可重复执行 |

#### 4.1.4 五福周报（P1）

| 项 | 内容 |
|---|---|
| 描述 | 每周一生成五色 + 白色各 SKU 的经营周报 |
| 内容 | 各 SKU 销量/毛利、明星菜品、原料价波动、下周建议 |
| 形式 | 卡片 + 可分享图 |

#### 4.1.5 预警中心（P0）

| 项 | 内容 |
|---|---|
| 描述 | 主动推送异常，老板无需主动查询 |
| 预警类型 | 库存跌破安全线、某 SKU 销量异常涨跌、原料采购价偏离历史均值、临期 |
| 阈值 | 管理后台可配 |

### 模块二：智能菜谱与厨师 SOP AI（新增 · 基于 docx）

> 本模块把非遗配方从文档变成"可算账、可执行、可品控"的活数据。

#### 4.2.1 智能菜谱（配方中枢）

**F1 配方结构化入库**
- 将附录 A 的 SKU 矩阵（面皮色 × 馅料）结构化存入"菜品配方"模块扩展表：面主料/主料/辅料/调料/制作方法/工艺参数/食养标签/五福寓意。
- 字段扩展：面皮色、馅料、单剂子重（10–11g）、成品重（25–27g）、醒发时长、点水次数等关键工艺参数。

**F2 用量换算**
- 输入"今日红色饺子 500 份"→ 按配方 BOM × 份数，展开各原料用量（面粉/火龙果汁/猪前肩肉/冬菇/荸荠/各调料）。
- 复用现有 `calcQtyOf`（结构测算只读层），不新写算账逻辑。
- 输出：采购清单草稿，可一键转"补货建议/采购管理"。

**F3 缺料替换建议**
- 当某原料库存不足或外接比价缺货时，AI 给替换建议。
- 约束：五色由天然果蔬汁决定，色绑定五福文化，**不可随意替换色源**（红色必须火龙果）。替换仅限辅料/馅料维度（如荸荠不足可调量或备注影响）。
- AI 输出：替换方案 + 成本/口味影响说明 + 是否影响"非遗出品标准"标记。

**F4 成本联动**
- 换算后调用 `dishRecipeCost()`（受保护函数，只调不改）算单份成本/毛利。
- 原料价格变动（外接比价）自动重算，老板 App 可见毛利波动。

**F5 食养与文化标签**
- 每色标注五福寓意（红=长寿、黄=富贵、绿=康宁、紫=好德、黑=聚财、白=团圆）、食养属性、过敏原。
- 用于点餐推荐与文化营销。

#### 4.2.2 厨师 SOP（执行与品控）

**F6 工序拆解与工单生成**
- 把每 SKU 的"制作方法 20 步"拆为结构化工序：和面 → 醒发 → 备馅料 → 拌馅 → 切剂擀皮 → 包制 → 煮制 → 装盘。
- 每工序字段：工序名、时长、工具设备、投料清单、操作要点、质检点、风险提醒、关键参数。
- 按"开餐时间"倒排时间线生成当日工单（如 11:30 开餐 → 10:00 和面醒发 → 10:30 备馅 → 11:00 包制 → 11:20 煮制）。

**F7 厨师端工单执行（厨房平板）**
- 工序列表，每步可计时、勾选完成、异常上报。
- 关键工艺 AI 提醒：醒发到时、料水分三次加入、分三次点凉水、剂子重量核查。
- 多锅/多 SKU 并行排程，避免工序冲突。

**F8 AI 品控抽查**
- 成品重量标准（25–27g/部分 25–28g）→ 厨师录入抽检重量，AI 判定合格率。
- 剂子重量（10–11g）、褶纹规整度（拍照 AI 识别，P2）。
- 不合格自动记录并推送厨师长/老板。

**F9 新人培训跟做**
- 交互式 SOP：新人按步跟做，AI 在关键工艺点抽查提问（"醒发几分钟""点水几次"）。
- 通过率记录入档，作为上岗依据。

### 模块三：管理后台增强（在已有上加，不重写）

#### 4.3.1 AI 助手配置 tab
- 简报推送时间、预警阈值、AI 可读模块范围、LLM 模型与成本开关。

#### 4.3.2 店务日历 tab
- 把进销存的离散动作串成时间线：周一补货日、周五对账日、月末盘点。

#### 4.3.3 配方管理 tab（扩展现有"菜品配方"）
- 承载 F1 结构化配方；支持新增 SKU 变体（新馅料）。
- 版本化：配方变更留版本，可回溯（非遗出品可追溯）。

## 5. 用户故事（核心场景串讲）

**US1 老板的早晨**
早 8:00，老板收到 App 简报："昨日营收 ¥X，毛利 Y%；今日补货待办 3 条；火龙果汁库存仅够做 2 天红色饺子，建议补货；美团待结算 ¥Z。"老板点"查看"→ 详情 → 一键确认补货转单。

**US2 老板的提问**
老板问 App："上周黑色三鲜饺子毛利多少？"AI 调结构测算 + 菜品配方，回卡片："上周黑饺销量 N 份，毛利 M%，原料墨鱼汁价格环比涨 8% 拉低毛利 1.2pct，建议：…"

**US3 厨房的上午**
厨师长在厨房平板看今日工单：11:30 开餐，10:00 和面醒发（5 色面团并行），10:30 备馅，11:00 包制，11:20 煮制。醒发到时 AI 提醒；包制时 AI 提醒"剂子 10–11g、成品 25–27g"。抽检重量录入，AI 判定合格率。

**US4 新人上岗**
新厨师跟做红色饺子 SOP，AI 在"料水分三次加入""分三次点凉水"处抽查提问，通过后记录上岗。

**US5 配方→采购贯通**
今日出品计划 500 份红饺 → F2 用量换算 → 采购清单草稿 → 转补货建议 → 老板一键确认 → 落库 → 次日进货入库。

## 6. 技术方案

### 6.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 老板 App-iOS | Swift + SwiftUI（或 UIKit） | 原生体验，符合决策 |
| 老板 App-安卓 | Kotlin + Jetpack Compose | 原生体验 |
| 双端共享模型 | Kotlin Multiplatform（KMP）共享业务逻辑/数据层 | 控制双端重复，UI 各自原生 |
| 云端 BFF | 轻量后端（Node/Go/Python 任一，建议与现有 Python 一致） | 与店内栈一致，降低维护 |
| 店内新增 | Python（与 server/ 同栈） | 复用 http 框架 |
| AI 决策层 | 本地确定性函数 + 云端 LLM（理解/生成） | 计算确定，生成灵活 |
| 数据库 | 店内 SQLite（主，不动） + 云端只读副本 | 本地为主 |
| 厨师 SOP 端 | 厨房平板 H5（嵌入 App WebView 或店内浏览器） | 低成本、易更新 |

### 6.2 云端 BFF 接口契约（关键，初版）

```
GET  /api/snapshot/latest        最新快照（rev, 生成时间, data 摘要）
GET  /api/report/daily           今日简报
POST /api/agent/chat             {question} -> {cards[], suggestions[]}
GET  /api/actions                待确认动作列表
POST /api/actions/{id}/confirm   确认 -> 入队, 返回 {status:queued}
GET  /api/actions/{id}/status     查执行状态
GET  /api/sop/workorder?date=     今日工单
POST /api/sop/qc                  质检录入
```

- 鉴权：老板 App 用账号+设备指纹+token；店内端走现有机制。
- 限流：对话接口按用户限流，控 LLM 成本。

### 6.3 快照推送与写回队列

- **快照推送器**（店内 cron，如每 15 分钟）：`GET /api/db` → 推云端只读副本；仅推 JSON+rev，体量可控（可按模块增量，P1 优化）。
- **队列消费器**（店内，每 30 秒拉取）：拉云端"确认动作" → 校验业务规则 → 调 `/api/sync` 落库 → 回写状态。
- **冲突处理**：若店内 rev 已变（店长刚操作），消费器按三向合并处理或回退为"需人工确认"。

### 6.4 AI 决策层架构（只读+确认）

```
用户问题
  ↓ 意图识别(LLM)
  ↓ 路由到 查询函数(确定性)
  ├─ 经营概览查询
  ├─ 结构测算 calcModel/calcQtyOf(只读)
  ├─ 库存查询
  ├─ 补货建议 restockLineOf(只读)
  ├─ 菜谱用量换算(新增, 调 calcQtyOf)
  └─ SOP 工单生成(新增)
  ↓ 结果回传 LLM 生成卡片
  ↓ 附带"建议动作"(可确认)
```

红线：写操作一律转"建议动作"，不直接落库。

### 6.5 智能菜谱/SOP 数据建模

新增两张表（与现有 SQLite 共库，仅增不改）：

- `recipes`：sku_id, name, color, filling, face_main(JSON), main(JSON), aux(JSON), seasoning(JSON), steps(JSON), params(JSON), blessing, diet_tags, version, updated_at。
- `sop_steps`：sku_id, step_no, stage(和面/醒发/…), duration_min, tools, inputs(JSON), key_points, qc_point, risk, params(JSON)。
- `sop_workorders`：date, sku_id, qty, planned_start, status, qc_records(JSON)。
- `qc_records`：workorder_id, sku_id, sample_weight, pass, ts。

复用现有 `dishes`/`ings`/`sales`/`orders`，外键关联，不改动既有字段。

## 9. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 原生双端成本高、周期长 | 高 | 用 KMP 共享业务/数据层，UI 各自原生；UI 组件复用；先 iOS 后安卓灰度 |
| 数据时延致老板误判 | 中 | UI 明示更新时间；写操作走确认队列保证最终一致 |
| 写回异步，老板重复点 | 中 | 状态机+rev 锁；"待执行/已执行"可见 |
| LLM 算错毛利/成本 | 高 | 业务计算交给本地确定性函数，LLM 只取数生成；关键数字二次校验 |
| 破坏计价/库存红线 | 高 | 新增表与红线逻辑解耦；用量换算只读调函数；变更走 [EDIT_PLAN] |
| 厨房网络不稳定 | 中 | 厨师 SOP 本地优先，离线可做工单，在线同步 |
| 配方结构化工作量 | 中 | docx 已结构化清晰，附录 A 可直接入库；分批录入 5 色+白色 |
| 色源不可替换约束 | 中 | 替换建议限定辅料/馅料维度，色源锁定 |
